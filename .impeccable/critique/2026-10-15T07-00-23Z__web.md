产品辨识度：风险、审批、实验与发布关联是特色；整体视觉是紧凑后台，保持现有风格即可。
优点：总览任务导向；发布预览、差异与并发冲突保护；双语、主题和移动端记录卡已实现。
自动扫描没有命中规则，这不代表业务流程没有问题。六组前端契约检查通过：render、preset、capability、flag_publish、rollout、i18n。

优先问题：
1. P1 未保存保护路径不完整。web/app.js:2909 的 popstate 恢复路由后直接重渲染，未调用 confirmLeaveEditor；应统一守卫返回/前进/页面切换并在取消时恢复地址与页面状态。建议 harden。
2. P1 结构化编辑仍依赖 JSON。web/flag_editor.js:28、31、88：条件为 JSON 数组、分组为逗号文本、所有值 JSON.parse。web/segment_editor.js:140 仍 JSON.parse 条件值。改字段/操作符/类型化输入，分组可搜索选择，常用模板只填写业务参数。建议 clarify、harden。
3. P1 发布流程缺少明确下一步。web/app.js:1297 同屏七个生命周期动作，gateActions 按权限裁剪。按草稿状态突出当前主操作，展示编辑→待审→已批准→已发布，危险操作独立，明确保存不等于生效。建议 distill。
4. P2 错误定位和网络恢复薄弱。web/app.js:88 提示 4.3 秒移除，复杂错误串接，字段缺少关联；api:108 未设显式超时/取消。持续错误清单、字段定位、重试与保留输入；写请求不盲目重试。建议 harden。
5. P2 编辑页信息密度与术语。baseRevision 可编辑、发布 JSON 和 GFF 导入常驻；中文页暴露原始 action/reason。配置、记录、高级工具分区；人类可读策略摘要；已知原因显示可执行说明，原始数据留诊断详情。建议 layout、clarify。

认知负荷：七动作及高级字段同屏是主要问题；导航已有分组，不应机械删减。选模板时轻松，编辑条件重新要求 JSON 形成体验落差，发布确认是已有安心点。
角色：新手卡在 JSON；熟练操作者多次滚动和判断下一步；键盘/读屏用户难逐一处理短暂错误。
次要观察：逐步拆分 app.js 降低维护成本；移动端已有基础适配，后续重点实测长规则、长标识符和键盘场景。
待决定：先做保护与错误恢复，还是同时推进无 JSON 的策略配置和发布动作收束？
