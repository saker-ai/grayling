## 0. 如何使用本文

本文是跨产品、服务端与 Web 的总交付路线。领域和协议细节见[增长实验实施方案](增长实验实施方案.md)，逐页字段与状态见[Web 控制台页面规格与交付清单](Web控制台页面规格与交付清单.md)，技术阶段与已有验收见[Web 控制台重设计实施方案](Web控制台重设计实施方案.md)和[Web 管理覆盖矩阵](web-management-coverage.md)。冲突时先核对实现与 API，再同步修改三份规格。每个工作包在任务单中引用本文的编号，验收证据归档到 `docs/acceptance/`。

**产品定位：**Grayling 是灰度发布和实验决策台。一个团队可以在这里定义变更、审查影响、稳定分流、验证真实曝光和指标、决定放量或回退。业务服务继续拥有用户身份、业务事件生产与营销触达；Grayling 只接收受控事实并作发布和实验决策。这条边界避免将控制台扩展成 CRM 或通用数据仓库。

**用户与典型时刻：**发布负责人在值守时快速找出需要暂停或推进的计划；实验负责人创建可解释、可重算的实验；分析员调查 SRM、漏损和水位；审批人在不访问原始用户事件的条件下审核变更；运维人员定位配置、Nacos、凭证和服务故障。Web 的主模式为 **Operate**：先让人看懂当前事实和下一步，再展示完整证据。

## 2. 北极星任务与产品度量

**首要任务：**用户进入某个工作空间和环境后，在十秒内能说清“哪个发布或实验需要我行动、有什么证据、下一步由谁执行”。十秒是设计走查目标，不是未经测量的效率承诺。

| 度量 | 事件/分母 | 首批基线与目标 |
| --- | --- | --- |
| 关键任务成功率 | 发布、回滚、创建实验、诊断 HOLD、审批、暂停/恢复各自的完成数 / 开始数 | 先做 5 人任务走查和浏览器事件基线，再在试点中评估改版变化 |
| 危险动作复核质量 | 有明确对象、环境、影响、证据版本和理由的操作数 / 全部危险动作 | 验收必须 100%；服务端缺字段即未通过 |
| 诊断可达率 | 从实验首屏在两次导航内到达首个真实阻断原因的比例 | 使用零样本、SRM、污染、护栏、水位五类样本逐项验证 |
| 错误恢复率 | 409/429/断网后保留输入并成功继续的任务数 / 可恢复失败任务数 | 基线先采集；危险操作不能因重试重复执行 |
| 数据可信标注率 | 显示结论的页面中同时显示口径、时间/水位、健康状态、版本的页面数 / 全部结论页面 | 设计验收 100% |

产品分析只记录页面、动作类型、成功/错误码、耗时与非敏感作用域标识；不记录 token、原始用户 ID、完整规则输入、Prompt 内容或报告的单元级事件。采样和保留策略随部署配置明确。

## 3. 全站信息架构与任务流

### 3.1 导航

```text
全局：Grayling / 工作空间 / 环境 / 会话状态 / 语言 / 主题 / 帮助
总览：待我处理、异常和近期变更
发布：Flags、Segments、发布历史
实验：实验列表、指标目录、实验工作台
AI 治理：资源、模型与兼容入口
审批：收件箱、待执行、历史
运维：求值调试、令牌、配额、审计
```

工作空间和环境是所有操作的固定上下文。切换前检查未保存输入，切换后取消旧请求、轮询和对象上下文；深链加载时先恢复会话再检查权限。审批是独立任务，不藏在审计内。列表支持可分享的非敏感筛选和返回位置；页面标题同时写对象、状态和作用域。导航顺序与用户的“发现→调查→决策→执行→追溯”顺序一致。

### 3.2 三条完整任务链

1. **安全发布：**总览风险/待审批 → Flag 当前版与草稿 diff → 受影响实验和 Segment → 提交审批 → 复核（提交人可自批）→ 发布 → 观察/审计 → 回滚入口。409 时保留本地草稿，显示服务器变化并要求再次复核。
2. **增长实验：**选业务假设 → 检查 Flag 与随机化单元 → 选冻结指标版本和护栏 → 选 `onDecision`/`onRender` 与接入负责人 → 创建 Draft → 评审和绑定检查 → 启动 → 分配/曝光/转化诊断 → 结果解释 → 分阶段放量或停止。每一步只执行其明确动作。
3. **值守恢复：**总览异常 → 实验工作台的当前阻断 → 诊断与报告版本 → 暂停/人工接管/回滚 → 审计与下一次安全观察窗口。紧急暂停和回滚保持可达；恢复、人工推进和交还自动控制需要当前报告证据。

### 3.3 页面间共享状态

URL 保存工作空间、环境、资源 ID、页签和非敏感筛选。授权事实只来自最新 capabilities；报告结论只来自服务端。离开作用域清空旧详情；浏览器后退不会重新提交 POST。表单临时草稿只在当前标签页内存保留，重新鉴权后只能由同一主体人工恢复。报告展示“生成于”和数据水位，缓存数据显式标为旧结果。

## 4. 整体 Web 体验重新设计

### 4.1 视觉与交互方向

界面采用“运行态指挥台”的清晰、克制气质：深浅主题共用一套语义层级；中性色承载结构，蓝色指向可执行动作，琥珀/红色标记需要人处理的风险。首屏用一条状态带把对象、环境、报告新鲜度和主操作连起来。证据区域以易扫描的表格、对照和时间轴呈现；装饰不占用故障与结论信息的空间。严禁只用颜色表达风险，也不把“计划完成”画成“实验胜出”。

设计 token 分四层：基础色与间距、语义色与文字、组件状态、图表编码。最小文字 14px（紧密表格附注可到 12px），数据/ID 等宽，主要结论 24–32px；间距采用 4/8px 级差。四类状态均需文本、图标或形状双重标识：正常、等待、阻断、不可用。组件库先定义状态带、对象摘要、证据面板、结构化 diff、步骤时间轴、可筛选列表、记录卡、确认框、空/错误模板、权限说明。视图复用这些组件，而不是复制模板字符串。

**页面构图：**桌面 1440px 使用固定导航、主内容与按需证据侧栏；1024px 收成单列主内容；768px 折叠导航；390px 变为标题→决策→证据→安全操作区。手机上的表格转记录卡或“关键列+详情”，页面不得整体横向滚动。主要触控目标 44×44px。滚动中固定动作区要给内容和输入法留空间。

### 4.2 全站页面蓝图

| 页面组 | 第一屏的结论与操作 | 深入页和数据表达 | 关键异常与权限 |
| --- | --- | --- | --- |
| 总览 | “需要我处理”的真实列表：阻断实验、待我审批、放量下一步、发布失败；每项有时间与直达链接 | 近期变更、各模块独立刷新、覆盖范围提示 | 某模块失败只标该模块不可用；超过查询上限不能显示“无风险” |
| Flag | 当前服务版、草稿状态、影响对象、审批进度；主动作是编辑或送审 | 结构化编辑与高级 JSON 共用同一草稿；发布 diff、版本历史、回滚目标 | 草稿冲突显示新旧差异并保留输入；无权限时可读内容与所需角色清晰分开 |
| Segment | 已发布条件、引用 Flag 数与路径、样本预览；主动作是编辑 | 条件构建、引用、草稿/发布对比与版本历史 | 预览只回答给定上下文是否命中，不称为人群规模；引用循环由服务端拒绝 |
| 实验列表 | 状态、健康、首个阻断、负责人/更新时间；主动作新建或打开 | 搜索、筛选、分页，带真实报告摘要 | 报告不可用与未运行分开；列表批量重算有上限和范围说明 |
| 实验创建 | 当前五步、每步完成情况与最终不可变契约；主动作下一步/创建 Draft | Flag 前置、分流、指标护栏、曝光接入、复核 | 返回上一步保留输入；错误摘要定位字段；创建前重新读取 Flag 和指标版本 |
| 实验工作台 | 状态→能否推进→首个原因→下一步；当前报告版本与水位可见 | 四区：决策摘要、数据健康、效果证据、放量时间轴；预注册/审计另页 | 零样本、未成熟、SRM、污染、护栏破线、报告失败各有独立文案和动作 |
| 指标目录与报告 | 指标定义/版本/归因窗；报告先给口径、健康与结论 | 分配→曝光→转化流、主指标区间、护栏、质量、独立方法视图与导出 | Bandit 使用奖励/反馈/冻结语义；不可重算报告标预览；图表有同数据表格 |
| 放量 | 当前 step、比例、最早判定时间、上次门禁；主动作按状态决定 | 完整阶段时间轴、理由、审计、回退位置 | 交还自动控制和人工推进确认当前证据版本；证据变更要求重新核对 |
| 审批 | 待我处理优先；对象、申请人、风险和到期状态 | diff、影响、策略、申请理由、批准/拒绝/执行分步 | 自批与自拒均可用（自审入审计）；过期基线重读；拒绝原因和失败输入保留 |
| AI 治理 | 当前 pin 版、撤销状态、来源/入口；主动作按能力显示 | 历史、解析预览、模型白名单、受影响入口 | 未有可信依赖/健康 API 时显示“未知”或隐藏；敏感内容按独立权限读取 |
| 运维 | 调试说明“无曝光”；令牌列作用域/到期；配额列当前/上限；审计列最近操作 | 命中路径、令牌撤销、修改影响、服务端筛选审计 | 令牌明文只显示一次；调试不记录曝光；429 与配额诊断相连 |

每页的字段顺序、API 和手机状态在[逐页清单](Web控制台页面规格与交付清单.md)中追踪。新增反向依赖、外部 Nacos 健康或“影响人数”必须先有服务端可信数据源；没有数据源时不放模拟数字。

### 4.3 关键组件契约

| 组件 | 内容 | 行为和验收 |
| --- | --- | --- |
| 决策状态带 | 状态、环境、更新时间/水位、报告版本、首个阻断、主动作 | 缺失/陈旧/不可用区别明确；状态改变通过 live region 通知；宽屏一行、手机分层 |
| 样本流程 | 分配、真实曝光、有效转化的唯一单元数与排除原因 | 绝不以求值数冒充曝光数；每一步可打开诊断明细；无数据不用 0% 成功色 |
| 结果证据卡 | 指标名和版本、单位、分母、两臂值、差值与区间、方法 | 统计口径固定；固定样本、序贯、贝叶斯分开；bandit 不复用胜出卡 |
| 危险动作确认 | 对象、环境、现状态、目标状态、影响、回退路径、当前证据版本、理由 | 打开和提交前重读；服务端 409 时停留并展示新证据；不清空理由；完成后跳审计/时间轴 |
| 结构化 diff | 草稿和已发布的字段级增删改、版本与申请人 | 长字段折叠仍可展开；仅已保存的服务器数据称为草稿；屏幕阅读器能读出变化类型 |
| 错误/空态 | 发生什么、影响范围、下一步、最近成功时间 | 401/403/409/429/5xx、断网、无对象、无事件、未成熟分别设计；可恢复错误保留输入 |

### 4.4 文案、无障碍与反馈

中文和英文同时设计，业务术语建立对照表：分配、曝光、转化、数据水位、HOLD、放量完成、统计结论。日期显示用户时区，cohort 另标业务时区。所有服务端错误用“事实→影响→行动”结构表达，不把 HTTP 码当唯一文案。表单错误同时出现在字段旁和顶部摘要；权限不足显示资格说明而非伪装成格式错误。这个设计借鉴 [GOV.UK 的验证错误恢复模式](https://design-system.service.gov.uk/patterns/validation/)；状态通知遵循 [WCAG 2.2 的状态消息要求](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。

目标为 WCAG 2.2 AA：标题与地标、标签、键盘焦点、焦点恢复、对比度、200% 缩放、减少动画偏好、图表文本等价物。44px 是产品触控目标，与标准最小尺寸区分。确认框须有焦点陷阱、Esc 行为、提交中防重复、成功后焦点落点。页面刷新、语言/主题切换和轮询不能把焦点无故移走。

| P7 全站质量 | 模块拆分、状态组件、响应式、i18n、无障碍、性能 | 各页面稳定后并行收口 | 四宽度、双主题、双语言；角色/错误矩阵；关键任务走查和性能预算通过 |
| P8 有限导入（可独立后置） | 带源水位的受控批次导入和可重算证据 | 增长实验方案 §7 的事件协议 | 幂等、撤销/修正、迟到、跨租户、失败批次不前移水位；导出可核对 |

### 5.1 前后端契约与数据来源

- Web 读取一次页面必需的读模型，避免每张卡各自无界请求。若现有 API 无法可靠汇总“待我处理”，新增服务端分页汇总，返回每模块的覆盖范围与局部失败，不计算伪总数。
- 报告和导出统一携带 experiment、epoch、注册/指标版本、生成时间、水位、健康状态及证据版本。放量写 API 接收期望证据版本，服务端在状态变更前重算并比较；历史和审计记录所用版本。
- 影响范围只用服务器维护的 Flag/Segment/实验/AI 入口依赖关系。反向索引更新与发布同一事务或有明确水位，UI 显示其截至时间；不能从浏览器可见列表猜测“全部受影响对象”。
- 每个写请求提供幂等或条件提交语义；至少使用现有 revision/hash 或报告版本作为并发检查。401、403、409、429、5xx 保持清晰错误码。权限、审批和统计门禁由服务端最终执行。
- 数据来源标签为“可重算”“预览”“未成熟”“不可用”。标签由服务端 `window.backend/recomputable/complete` 等真实字段决定。外部 Nacos 健康也必须有真实检测与最近成功时间。

### 5.2 Web 代码演进

当前 `web/app.js` 管理路由、状态、API 和大部分页面。按页面包逐步拆成 `shell`/`scope`/`api`/`components`/`pages`，先抽公共错误、确认框和生命周期，再迁移单个视图。保留当前内嵌静态资源部署；模块边界和构建方式在 P7 用加载性能数据决定，不预设必须引入框架。路由卸载时取消 fetch/轮询，报告只在页面可见且相关状态运行时刷新；失败退避并可手动重试。UI 不计算统计显著性或自动放量结论。

## 6. 验收矩阵与发布顺序

**角色×状态：**至少用发布人、审批人、分析员、只读者；对创建、发布、审批、诊断、放量、AI 撤销、令牌管理分别验证“看得见什么、能点什么、服务器准不准”。跨工作空间深链不得泄漏对象名称或内容。

**数据×故障：**无对象、无分配、已分配未曝光、健康有数据、SRM、污染、护栏破线、水位未到、报告不可用；另覆盖 401、403、409、429、503、断网和部分汇总失败。每个关键操作验收失败时的页面与持久状态，不只验收成功 toast。

**设备×辅助技术：**390、768、1024、1440px；中英文、深浅主题；键盘全路径、屏幕阅读器的导航/错误/弹窗/状态通知；200% 缩放与减少动画偏好。桌面和手机都完成发布、实验诊断、审批、暂停三条关键链路。

**系统×数据：**JSON、GORM SQLite、GORM PostgreSQL、原生 PostgreSQL 在适用范围内做控制面读写与重启；确认性报告与事件重算仅在满足原始事实和保留期的后端验收。多副本对并发写和报告版本冲突做真实进程测试。P1–P8 不得用模拟前端数据代替服务端证据。

发布按“内部试点→单工作空间→多工作空间”推进。每次启用新能力前核对数据水位、事件接受/拒收率、报告重算耗时、放量暂停原因和操作失败率。若异常，关闭新入口或自动推进，保留历史事实与审计；回退 UI 不删除已写事件。每个阶段签收前更新 OpenAPI、用户文档、操作手册与 `docs/acceptance/` 证据索引。

## 7. 尚需产品决定的输入

这些决定不影响已明确的安全门和基础页面：实验负责人字段从何处取得、哪些环境允许紧急停用、AI 入口反向依赖的可信数据源、企业品牌资产、试点业务的漏损阈值。没有可靠答案时以“未知/需人工复核”显示，不推断人数、健康或允许动作。决定后写入领域注册/配置与验收样本；运行中 epoch 的确认性口径不能追溯改写。

## 8. 参考与取舍

- [LaunchDarkly 的审批工作流](https://launchdarkly.com/docs/home/releases/approvals/)提供变更申请与角色审查模式；Grayling 采用提交 → 审核 → 执行的审批流程，不排除提交人自批（自审入审计），仅紧急操作的事后复核要求原操作者以外的人完成。
- [LaunchDarkly 的发布模式](https://launchdarkly.com/docs/fed-docs/home/releases/releasing)区分百分比放量、受监控放量与实验；Grayling 的 UI 也明确区分“发布完成”和“实验结论”。
- [LaunchDarkly 的指标版本说明](https://launchdarkly.com/docs/fed-docs/home/metrics)支持运行中固定指标口径的设计选择；Grayling 以注册版本和指标快照实现同类可追溯性。
- [GOV.UK 错误恢复模式](https://design-system.service.gov.uk/patterns/validation/)和 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)用于表单错误、状态通知、焦点与触控验收。外部产品仅提供模式参考，不替代 Grayling 的实际 API 和统计规则。
