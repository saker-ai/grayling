# 增长实验能力规划

> 状态：分阶段实施中，2026-10-13。指标目录、版本冻结与显式曝光基础协议已经实现；诊断与放量门、数据导入及完整 Web 重设计仍在实施。现有行为以 [API 参考](api.md)、OpenAPI 和代码为准。

完整落地规格见 [增长实验实施方案](增长实验实施方案.md)；管理台的全站产品与交互改版见 [Web 控制台重设计实施方案](Web控制台重设计实施方案.md)和[逐页交付清单](Web控制台页面规格与交付清单.md)。

## 定位与职责

Grayling（应用名 GoLab）负责实验决策闭环：受众定向与稳定分流、实验预注册、曝光和转化归因、数据健康检查、效果报告、渐进放量与回滚。业务系统负责用户身份、页面和业务流程、消息发送、优惠券与奖励、交易，以及渠道归因。数仓和 BI 可提供业务指标来源和长期分析；Grayling 不复制其全量用户画像与行为日志。

```text
业务系统：识别用户、执行体验与业务动作
       ↓ 求值上下文 / 实际曝光 / 转化事件
Grayling：分流 → 归因 → 数据健康 → 实验报告 → 放量或回滚
       ↓ 结果和决策
业务系统 / BI：执行发布、复盘和后续运营
```

因此，“增长”在本项目中指**通过可验证实验改善激活、留存和收入等产品指标**，不指获客投放、CRM 或营销自动化。

## 业界方案与取舍

以下参考各产品的官方文档。表中的“Grayling 取舍”是本项目的设计建议，不表示这些能力已经实现。

| 方案 | 经验证的做法 | Grayling 取舍 |
| --- | --- | --- |
| [GrowthBook：指标与事实表](https://docs.growthbook.io/app/metrics)、[SDK 曝光回调](https://docs.growthbook.io/lib/js) | 基于数仓事实表定义指标；SDK 在实验分配时调用可接入分析系统的回调 | 借鉴“曝光与指标事实可独立采集、可重新计算”的数据模型。首轮仍使用现有实验事件存储，P3 仅导入已归因的指标事实，不建设 SQL 查询引擎。分配回调不能自动等同于用户真正看见页面。 |
| [LaunchDarkly：指标](https://launchdarkly.com/docs/home/metrics/)、[渐进发布](https://launchdarkly.com/docs/fed-docs/home/releases/releasing) | 指标可跨实验复用；运行中的实验固定所引用的指标版本；实验分析与发布期监控有各自的入口 | P1 建立版本化指标目录，报告记录所用版本；保留现有实验决策与放量护栏两套语义，避免把“无异常可继续放量”解释为“实验变体已胜出”。 |
| [Statsig：手动曝光](https://docs.statsig.com/server-core/node-core)、[SRM](https://docs.statsig.com/experiments/monitoring/srm) | 默认求值可记录曝光，也允许延迟至实际使用时手动记录；SRM 用于发现分配或采集问题 | P1 提供明确的曝光模式和幂等契约；P2 把 SRM、曝光缺失和归因异常作为可定位的数据健康问题。手动曝光容易漏报，接入示例和诊断必须同时交付。 |
| [OpenFeature：求值上下文](https://openfeature.dev/specification/sections/evaluation-context/)、[Tracking 规范](https://openfeature.dev/specification/sections/tracking/) | `targeting key` 标识定向主体；Tracking 将求值后的业务动作与指标数据关联 | 统一 SDK 的身份和事件命名；沿用已有 OpenFeature 接入，不另造一套通用特性开关标准。 |

这些方案共同强调可追溯的分配、曝光、业务指标和数据质量。Grayling 最适合先补齐这一条链路，再根据接入需求扩展数仓连接；营销编排、全量行为分析、自动分群和通用 BI 不进入本规划。

## 第一条试点链路

选择“新用户首次关键操作”作为首个增长实验：同一业务服务通过一个 Flag 展示两版引导，主指标为首次关键操作完成率，D1 留存为护栏。业务系统提供稳定的用户 ID，实际完成操作时上报转化；实验预注册样本、最短运行期和分析窗口，先小流量运行，再根据报告人工或自动推进放量。

试点验收须逐项证明：同一单元始终进入同一变体；曝光与转化使用同一随机化单元；事件重试不重复计数；报告能解释样本不足、SRM、迟到事件和未成熟留存 cohort；护栏破线可阻止推进；回滚后新请求不再进入被停止的实验。试点先使用现有 API 和 SDK，不以开发新模块为前置条件。

## 目标数据契约

1. **身份与分桶。** 每个实验在注册时固定 `unit`，例如业务用户 ID；业务系统传入稳定的 `targetingKey`，避免使用邮箱、手机号等原始个人信息。匿名用户登录、跨设备和账号切换的规则必须在实验开始前确定，同一实验期间不能悄悄更换分桶单位。OpenFeature 的 [evaluation context 规范](https://openfeature.dev/specification/sections/evaluation-context/)也把 targeting key 作为定向和比例分流的主体标识。
2. **决策与曝光。** 为实验预注册曝光模式：`onDecision` 用于求值后必然执行的服务端动作；`onRender` 用于可能未展示的页面组件。后一模式只有实际展示时才提交曝光，同一决策重复展示需按已定义的去重单位处理。现有远程求值自动记录曝光，新增模式须明确 API/SDK 行为与迁移方式；禁止同时自动和手动记录同一次曝光。
3. **指标定义。** 为业务指标登记稳定的 key、业务含义、事件来源、数值类型、去重单位、归因窗口、负责人和定义版本。实验注册时固定指标版本；定义变化需要新版本或新 epoch，不重写已运行实验的确认性结论。只有预注册的主指标和护栏可以进入自动决策门。
4. **事件与归因。** 曝光和转化沿用 `experimentId`、`epoch`、`variant`、`unit`、`eventId`、`metricKey`、`clientTime` 等现有字段。SDK 可提供更易用的封装，但服务端仍校验作用域、epoch、时间窗口和幂等性。需要从数仓导入指标时，只导入可归因到实验与单元的指标事实，不建立全量通用事件库。
5. **数据安全。** 原始用户 ID 仅用于请求处理，沿用工作空间内 HMAC 伪名化；不在报告或日志输出原始身份。浏览器不持有管理凭证，采集入口通过业务后端或受控代理接入，并遵守工作空间配额和保留期。

**P1 契约与进度：** 指标目录已按 `(workspace, key, version)` 标识不可变定义，实验创建时可固定主指标及护栏的版本和定义快照，报告展示来源；修订定义创建新版本，运行中的实验仍按原版本计算。已支持主指标和护栏分别采用不超过实验分析窗口的冻结归因时长，并从同一原始事件快照逐指标重放。若事件来源或分母口径变化会影响确认性结论，应开启新实验或新 epoch，而不是在原报告上覆盖结果。

曝光在语义上区分“被分配到变体”和“确实触达变体”。`onDecision` 适用于决策必然生效的服务端路径；`onRender` 的远程求值现已返回不透明、短时、作用域绑定的曝光凭据，业务端确认实际展示后提交曝光。Go/Python/TypeScript SDK 已提供显式曝光调用，本地 Go SDK 同批发送分配与曝光，服务端核对并幂等写入。未触达的分配只应计入诊断，不进入效果分析的曝光分母；跨变体污染与漏损必须在诊断和自动放量门中阻断，此部分仍在实施。凭据 15 分钟有效，过期重新求值；重试保留稳定 decisionId 与 eventId。

OpenAI Chat Completions 入口有单独限制：目前分流单位由上游 Key 与可选 `user` 字段共同哈希。多人共用同一 Key 且不传 `user` 时，这些人会落在同一变体；仅修改 `baseURL` 无法识别终端用户。它适合模型和 Prompt 的入口治理，不能在缺少可信终端用户标识时声称完成用户级增长实验。见 [Chat Completions 契约](api.md#openai-兼容-chat-completions)。

## 实施顺序

| 阶段 | 交付范围 | 完成门槛 |
| --- | --- | --- |
| P0：真实试点 | 用现有 Flag、实验、SDK、采集与报告跑通上述激活实验；整理可复用的接入示例和运营步骤 | 端到端归因、数据健康、护栏和回滚均经真实业务链路验证；先用 A/A 或等价合成流量检查分流与埋点，再记录实际接入摩擦；A/A 通过不代表真实实验一定无偏 |
| P1：定义与曝光 | 增加版本化指标目录、事件命名规范和实验曝光模式；在创建实验时冻结定义 | 同名指标跨团队含义一致；未展示组件不计曝光；重复提交不重复计数；旧实验按原定义重算 |
| P2：接入与诊断 | 统一 Go/Python/TypeScript SDK 的决策、显式曝光和转化体验；控制台展示缺失事件、单位不一致、跨变体污染、重复事件、迟到水位及 SRM 线索 | 集成者可从一次决策定位到曝光、转化或明确的拒收原因；数据质量异常阻止自动推进，不能被误判为实验效果 |
| P3：有限的数据对接 | 按真实需求导入实验指标事实，并向 BI 导出实验结果与定义版本 | 对接链路可审计、可重算、可隔离租户；Grayling 不承担用户画像和通用 ETL |

每阶段先完成前一阶段验收，再确定下一阶段的具体 API 和存储变更。P0 不要求新的公共接口；P1/P2 的提议接口必须在设计评审后写入 OpenAPI 与 SDK 契约。D30 等更长留存、跨设备身份拼接和额外统计方法不作为首轮范围，由试点数据与产品需求决定。

## 发布与决策原则

- SRM、缺少曝光、身份口径不一致、原始事件不可重算、迟到水位未到或留存 cohort 未成熟时，报告应保持不健康，自动推进不得宣告成功。SRM 是分流或采集质量警报，不能把偏斜样本的指标提升当成效果；参见 [Statsig 的 SRM 指南](https://docs.statsig.com/experiments/monitoring/srm)。
- 自动推进继续遵守现有的预注册主指标、护栏、样本量和观察窗口；实验最后一步的放量完成不等于无条件全量发布。
- 不把固定样本 p 值、序贯结果和贝叶斯后验混成一个“胜率”；现有报告已将它们分开呈现，新增增长界面也应保持这一语义。
- 业务系统始终拥有最终业务动作。Grayling 输出分流决定和可审计的实验结论，不自动发送消息、发放奖励或修改用户账户。
