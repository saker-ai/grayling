机制说明：跨副本发布串行化 = PostgreSQL **session 级 advisory lock**（每 (workspace, environment) 一把，`Store.PublishLock`，独占池连接持锁）+ 锁内 `ReloadFromBackend`（revision 分配前看到对端全部已提交状态）；单进程内仍由 publishMu 先行串行化（文件/内存后端时为 no-op 锁，行为与单节点历史一致）。gonacos Redis pub/sub 为 fire-and-forget，断连窗口内的通知**会丢失**，故收敛兜底依赖发布对账后台任务（§11 行）；断连场景的实测 1.73s = 对账间隔 1s + 修复重发布耗时。副本重启场景同时覆盖 gonacos 外部 Redis 模式的启动装载与 PG 全量状态重建。

间歇失败根因与修复（2026-09-25）：该套件曾在全量套件并发/CPU 受限负载下以约 **11%**（35 样本 4 次，单跑与低负载 18 样本 0 次）间歇失败（`final snapshot missing concurrently published flag conc-0` / `final replicas disagree on eval(u1): A="control" B=""`），取证判定为**测试采样/等待语义缺陷**而非产品缺陷：gonacos pub/sub 按文档 fire-and-forget 同步，8 并发跨副本发布后的传播窗口内，副本 B 已同步到 manifest r12/r13（两副本 revision 均等于真终值）但个别 `grayling.flag.conc-X.r1` 文档尚未落地，读路径此时**按设计**拒绝服务不完整快照、返回 HTTP 500（`ErrIncompleteSnapshot`，§5.2"缺文档即中止、调用方保持旧状态"，1s 对账 tick 兜底收敛）；而旧测试 `fullSnapshot` 不校验状态码（500 错误体被静默解码成空快照→误报"manifest 漏键"）、`sdkEval` 把传输/HTTP 错误静默降级为 `""`（→误报"求值不一致"），且收敛等待从**滞后的副本服务视图**采样"终值"并只等单副本 `>=`（采样值偏低时立即通过，实际未等待收敛）。产品侧无缺陷证据：manifest 从未漏键（PG advisory lock 内由整库真值构建）、副本进程健康、窗口均在对账 tick 内自愈。修复只改测试：收敛等待一律以**已知真终值**为目标（发布响应的 manifestRevision / 无空洞校验过的 base+n / 4b 胜者 revision），`waitRevision` 语义改为"两副本都 >= want"、终扫改用"两副本 revision 相等且 >= 真终值"；快照/求值断言仅在**有界窗口**内重试传输错误/5xx（即上述文档同步窗口），而 HTTP 200 缺键、成功求值不一致、4xx、解码失败一律立即失败——产品缺陷可检出性不降反升。契约详见 `test/cluster/cluster_e2e_test.go` 文件头"Convergence-wait contract"。修复后同负载压测（GOMAXPROCS=2 + taskset 8 核 + 30 忙循环 + 全量套件并发——旧代码在该条件下 2/15 失败）**15/15 全绿**，单跑 **5 连绿**，全量 `go test ./... -race -count=1` **连续 3 轮全绿**（且 3 轮均在上述加压条件下运行，test/cluster 分别 16.9s/17.3s/18.9s）。

6. 浏览器/脚本场景：多语言 SDK（`sdk/python`、`sdk/typescript`）与浏览器一律走远程求值 `/api/v1/sdk/eval` + 受限投影 `/api/v1/sdk/revision`（可经 `cmd/grayling-proxy` 独立部署），**不下发全量快照**（SDK token 是服务端凭证，含内部规则，不得直接交给浏览器）。
7. 自动推进引擎使用共享 PostgreSQL 的数据库时钟租约选主（详见 [rollout 多副本运维](rollout-多副本.md)）；各副本可同时启用 `-rollout-interval`。运行中先检查租约，再按实验 advisory lock 重载状态；决策门查询后再次复核持有权，失去租约即停止动作。发布仍走现有事务与锁。**控制台 rollout UI 已落地**（原"计划与历史暂经 API/实验详情 JSON 查看、控制台 UI 未做"限制已解除）：实验详情 rollout 区块覆盖计划预注册、当前步骤与进度、计划步骤表（比例/观察窗/决策门推进方式/状态）、下次决策门评估时间、执行历史（含跳过/阻断原因）、暂停/恢复/手动推进/人工接管开关（危险动作 confirm+原因二次确认，与回滚确认风格一致），SRM/护栏阻断以报告同款警示样式醒目呈现；只调用既有 release-plan 路由，未新增端点。证据：`web/rollout_contract.mjs` DOM 契约测试（Node VM 加载真实 app.js，8 种计划状态+4 条操作流程全通过；`GOWORK=off go test ./web/ -count=1`）。

## AnalysisWindow 报告口径（Issue #1）

- 统一 UTC。实验首次进入 Running 的 `StartedAt` 是固定锚点；曝光的 `clientTime` 必须在 `[StartedAt, StartedAt + AnalysisWindow)`。同一实验和 epoch 的 split 曝光单元进入随机化分析集，其他来源仅展示曝光量。
- 转化须与曝光同 variant、同单元，`clientTime` 不早于该单元在窗口内的最早曝光，且早于窗口终点；单次曝光归因的最长时长也是 `AnalysisWindow`。窗口终点为开区间。事件 ID 在 PostgreSQL `event_index` 中全局去重。
- 采集时拒绝晚于服务端当前时间 5 分钟、早于当前时间 72 小时的客户端时间。报告水位为生成时刻减 72 小时；只有水位达到窗口终点、原始事件数与增量事件计数一致、原始转化总和与增量单元聚合一致，才标记完整。报告列出版本、开始/结束 UTC 时刻、水位、后端、`recomputable` 能力和缺失原因。
- 原始事件被保留期清理后，增量计数仍在，校验将报告缺失并阻止自动放量。内存/文件后端沿用全期增量聚合，报告 `backend=incremental`、`recomputable=false`；其 `complete` 只表示本地增量视图可用，不证明历史原始事件或预注册窗口完整。生产自动放量应使用 PostgreSQL。历史报告可用同一 epoch 的预注册参数及原始事件重算；已过水位的窗口不会再接纳符合迟到限制的新事件。

### Holm 多重比较（Issue #9）

- 固定样本确认性检验支持预注册单个 Holm 家族（2–100 项）：多个 mean/proportion 主指标及多变体有序臂对均须在创建时列入；首项绑定原主指标。护栏独立于家族并逐治疗臂检查，未注册比较仅为探索性。旧单主指标实验无家族时统计结果与决策逻辑不变。
- 报告逐项给出原始/调整后 p 值、排序、有效 alpha、拒绝结论，显示注册版本；版本含家族与决策契约并记入创建审计。API 无假设修改路径，报告对版本漂移 fail closed。序贯和 Bayesian 仍分别展示，不参与 Holm。
- 数值验收：[公开解析样例](https://en.wikipedia.org/wiki/Holm%E2%80%93Bonferroni_method) p=[0.01,0.04,0.03,0.005] 的 Holm 调整值=[0.03,0.06,0.06,0.02]、排序/逐步阈值/拒绝判定逐项通过；算法亦与 [statsmodels 的 Holm 实现](https://www.statsmodels.org/stable/_modules/statsmodels/stats/multitest.html)核对。固定种子 909、20,000 次、4 个独立真零假设的家族错误率 0.0479（目标 alpha 0.05）。多变体报告集成测试覆盖 SRM、不同主指标、adjusted gate 与注册副本隔离；另有双臂样例证明两个原始 p 值均小于 0.05、调整后均大于 0.05 时 verdict=continue；管理服务测试覆盖创建审计中的版本和家族。详见 `internal/stats/holm_test.go`、`internal/experiment/report_holm_test.go`、`internal/admin/experiments_holm_test.go`。
