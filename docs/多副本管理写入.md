# 多副本管理写入

共享 PostgreSQL 时，每个管理写入在同一数据库事务内对 `meta.control_version` 做条件更新。提交者必须持有其加载工作集时的版本；成功提交使版本递增。另一副本先提交时，本次事务不写任何对象，API 返回可重试的 `409 conflict`（含“reload and retry”说明），服务端重新加载工作集并丢弃失败尝试。调用方应重新读取对象、检查意图后重试；不要盲目重放会生成一次性密钥或触发外部发布的请求。唯一键冲突及 PostgreSQL 序列化失败也转为 `409`。

| 对象 | 数据库唯一性 | 并发版本/分配 |
| --- | --- | --- |
| workspace | `id`、`slug` | 全局 `control_version`；`meta.next_counter` 在同一条件事务内推进 |
| environment | `id`、`(workspace_id, slug)` | 同上，namespace 由已分配 ID 派生 |
| token | `id`、`secret_hash` | 同上；认证每次查询 PostgreSQL，撤销即时生效 |
| quota | `workspace_id` | 全局版本保护整份 quota 文档 |
| experiment 与 release plan | `id`；实验 epoch 的业务校验 | 全局版本保护状态/计划文档；计划动作另持有既有 plan advisory lock |
| flag、segment 草稿及发布状态 | `(workspace_id, environment_id, key)`；不可变 revision 另含 `revision` | 全局版本；发布另持有既有 scope advisory lock |
| AI 资源、pin、allowlist、撤销 | 范围键，pin 另含 `version`，allowlist 另含 provider/model | 全局版本保护整份范围记录和删除 |
| audit | `id` | `meta.next_audit` 随全局版本条件推进；插入冲突报错，无静默忽略 |

事件摄取不推进管理版本；它使用 `event_index` 去重账本和数据库内增量聚合，避免高频事件使管理请求持续冲突。文件/内存后端仍按单进程使用。管理读路径仍由各副本内存工作集提供，靠对账周期重载收敛；认证令牌查询直接走数据库，防止其他副本撤销后继续授权。不能把尚未收敛的管理列表用于实时授权决策。

锁顺序保持原有流程：release plan lock → publish scope lock → PostgreSQL 事务对 `meta` 行做条件更新。普通管理写入只使用事务行锁，不另取 advisory lock；事务失败/进程中断由 PostgreSQL 自动回滚和释放行锁。发布/计划 advisory lock 等待上限为一分钟。若因超时、死锁或版本冲突收到 `409`，重新读取后重试。部署前用 `go test ./internal/platform -run TestPGManagement -count=1 -v` 对真实 PostgreSQL 验证双进程创建竞争、跨副本撤销/审计、锁超时和连接中断后的释放。
