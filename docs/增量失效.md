# PostgreSQL 管理对象增量失效（Issue #3、#15）

`meta.control_version` 是管理写入的全局单调版本。迁移 v3 建立 `control_changes(version, collection, object_id, committed_at)`，与对象更新、版本递增在同一事务提交。`object_id` 是内存集合键的 base64url 编码，因为范围键包含 PostgreSQL `text` 不接受的 NUL。事务内 `NOTIFY grayling_control` 的 JSON 只含类型、ID、版本；接收方从真值表读取对象。事件摄取不推进此版本。

副本以已完整应用的版本为游标，按版本顺序读取日志。workspace、environment、token、flag/segment 草稿、修订历史、当前与下一个修订状态、环境 manifest revision、approval、experiment、quota、AI 资源与版本 pin/白名单/撤销及 audit 都按主键或作用域定向读取。删除记录会删除内存键；修订历史按该对象作用域重新读取，以覆盖发布和保留期裁剪。旧通知不能降低游标。同一版本的所有对象应用完才确认游标。发布仍在 PostgreSQL advisory lock 内强制重载后分配 revision，以保留跨副本单调性。

独立 `LISTEN` 连接断开后重连；每 500ms 查询 `meta.control_version` 和清理水位，无变更时不载入对象表。漏通知、断线与重启后会读取持久日志补账。版本空洞、单次超过 4096 行、未知集合或本地游标低于清理水位时，以经过版本校验的整库重载恢复。重载完成才确认新游标。若数据库不可达，同步失败并保持原游标；下一次轮询重试。`-reconcile-interval` 仍用于 gonacos 发布底座校验。

## 日志游标与安全清理

迁移 v9 建立单行 `control_journal_watermark.pruned_through` 和 `control_replica_cursors(replica_id, cursor, heartbeat_at)`。副本启动时完成全库读取并登记随机进程 ID 和游标；应用新版本后立即确认，闲置期间每 10s 续租。正常关闭删除登记；崩溃或断连后 30s 未续租的登记失效。清理器由副本的同步循环每分钟触发，持有水位行锁；取当前版本、所有未过期副本的最小确认游标，并且每事务最多推进 1024 个版本。删除 `version <= target` 的日志、更新水位、移除过期登记和读取剩余行数，均在同一事务中提交。并发清理器由行锁串行化。没有有效副本时，目标可到当前版本；重启副本先全量装载真值表再登记。失联副本若在租约内恢复，未确认日志保留；租约过期后恢复，若游标低于水位则全量装载，不尝试跳过日志。水位不会回退。运维不得单独删除日志行或改写水位。

清理按版本批次控制单次事务范围；一个版本若含大量对象，仍可能产生大事务，需观察日志行数和 PostgreSQL 锁等待。日志表的磁盘空间归还遵循 PostgreSQL vacuum 机制。清理期间若写入或确认失败，事务回滚，下一轮重试。日志已清理后的全量恢复需要主库可读；持续不可用期间不能保证管理列表收敛，但 token 鉴权仍直接查库并在查询失败时拒绝。

## 指标与告警

`ChangeSyncMetrics()` 和 `RunReconciler` 日志提供 `control_applied`、`control_queries`、`control_failures`、`control_version_lag`、`control_max_notification_delay`、`full_reloads`、`last_full_reload`、`control_fallback_reloads`、`control_journal_rows`、`control_journal_bytes`、`control_oldest_unconfirmed_cursor` 和 `control_pruned_through`。`full_reloads` 包含发布锁内主动重载；`control_fallback_reloads` 仅计同步协议回退。日志行数、表与索引占用字节数、最老确认游标是上次清理事务的快照，最多滞后一轮；水位在每次同步查询时刷新。关注持续超过 16s 的版本滞后、失败递增、正常单对象变更出现回退，以及日志行数持续增长或最老确认游标长时间不前进。活跃副本落后会阻止清理；断线超过租约则允许清理并在恢复时重载。

## 撤销与权限收紧

PG 模式下每次 token 鉴权都以 secret hash 查询主库。撤销或角色收紧提交后，下一次成功的鉴权查询即生效；数据库不可达或查询失败时拒绝鉴权。管理列表按失效协议更新。健康 PG 与正常调度下，漏通知最多等待下一次 500ms 轮询再加一次 15s 查询上限；持续不可用时没有有限收敛上界。

## 验证

真实 PostgreSQL 测试 `TestPGScopedFlagSegmentSync` 覆盖双副本 flag/segment 草稿、修订和状态、manifest、并发冲突与重启；`TestPGJournalPruneAndLaggedRecovery` 覆盖活跃滞后副本阻止清理、过期租约清理、回退和日志指标；`TestPGJournalPruneRollbackOnFailure` 验证删除失败时日志和水位同时回滚；`TestPGScopedIdleAndListenerRecovery` 覆盖 LISTEN 断连和闲置轮询。运行：`go test ./internal/platform -run 'TestPG(Scoped|JournalPrune)' -count=1 -v`。测试需 `GRAYLING_TEST_PG_DSN` 指向可创建临时数据库的 PostgreSQL，或 Docker 可启动 `postgres:16-alpine`。这些是本机集成测试，不代表生产拓扑的时延或容量保证。
