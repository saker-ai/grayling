# PostgreSQL 管理对象增量失效（Issue #3）

`meta.control_version` 是所有管理写入的全局单调版本。迁移 v3 建立 `control_changes(version, collection, object_id, committed_at)`，与对象更新、版本递增在同一事务提交。`object_id` 是内存集合键的 base64url 编码，因为部分范围键包含 PostgreSQL `text` 不接受的 NUL。事务内 `NOTIFY golab_control` 的 JSON 只含 `type`、`id`、`version`；接收方不读取通知中的对象状态。事件摄取不推进此版本。

每个副本以启动时载入的版本为游标，收到提示后查询 `control_changes`，再按主键从 PostgreSQL 真值表读取 workspace、environment、token、experiment、quota、AI 资源/版本 pin/白名单/撤销或 audit。旧提示不能降低游标；同一版本的所有对象应用完后才推进。若版本有空洞、单次积压超过 4096 行或遇到尚无定向读取器的集合（flag/segment 等），以校验版本的整库重载恢复。发布路径仍在 advisory lock 内强制重载，以分配单调 revision。

后台使用独立 `LISTEN` 连接，连接断开后重连；每 500ms 查一次 `meta.control_version`，无变更时仅一次索引/主键查询，不载入对象表。通知丢失、断线或进程重启后，持久变更日志仍能补账。日志目前不自动清理，运维应监控其行数；在没有全体副本确认游标之前不能安全按时间删除。`-reconcile-interval` 仍用于 gonacos 发布底座的周期校验，已不触发每 tick 整库重载。

## 撤销与权限收紧的可见性

PG 模式下每次 token 鉴权都以 secret hash 查询主库，直接使用返回的 `revoked`、`role` 和作用域。**撤销或角色收紧提交后，下一次鉴权查询即生效**；查询超时为 15s，数据库不可达或查询报错时 API 拒绝鉴权（401），不会按旧缓存授权。管理列表的 token 元数据按失效协议更新，在健康 PG 与正常调度下，漏通知最多等待下一次 500ms 版本轮询，加上一次 15s 查询上限；数据库持续不可用时列表新鲜度没有有限上界，但鉴权仍拒绝。其他管理对象同样由此轮询恢复；失败计数与版本滞后反映未收敛状态。

## 指标与成本基线

`RunReconciler` 日志每轮输出 `control_applied`、`control_queries`、`control_failures`、`control_version_lag`、`control_max_notification_delay`、`full_reloads` 和 `last_full_reload`。这些是进程累计/当前值，完整重载耗时只记录最近一次。`ChangeSyncMetrics()` 可供运行时集成读取。告警应关注非零版本滞后持续超过 16s、失败递增或全量重载频繁出现。

真实 PostgreSQL 测试 `TestPGChangeSyncMissedNoticeAndIdleCost` 的 100 次无变更轮询：**100 次版本查询、0 次全库读取**；一次本机样本为总耗时 32.1ms、分配 145,280 bytes，`HeapAlloc` 从 2,549,768 到 2,695,048 bytes。测试同时打印轮询前后 `HeapAlloc`，可在目标机器复测，不将该样本视为生产容量上限。定向变更消耗版本查询、日志查询和每对象一次主键查询；未知集合的变更仍需一次整库重载，其耗时和内存与数据量相关。测试命令：`go test ./internal/platform -run 'TestPG(IncrementalControlSync|ChangeSyncMissedNoticeAndIdleCost|ChangeSyncListenerReconnect)' -count=1 -v`。
