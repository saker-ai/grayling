## 1. 整体开发目标与边界

Grayling 要提供一套多工作空间的功能开关、渐进发布和可信 A/B 实验系统，服务传统后端、Web 应用与 AI Agent。控制面负责定义、审核、发布、分发和分析；数据面在应用或代理处按稳定身份求值。AI 增强的核心是把实验变体绑定到**不可变的资源版本**，使 prompt、模型、skill、AgentSpec、MCP 和 pipeline 的发布可分流、可归因、可回滚。

最终能力包括：布尔/字符串/数值/JSON 变体，优先级规则与 segment，固定分桶及互斥实验，按指标保护的发布流程，多语言 SDK 和 OpenFeature Provider，曝光与转化事件、统计报告、AI 资源解析、审批与审计、运维观测。Unleash、GrowthBook 是产品参照；其 SDK 全集、商业功能、所有统计方法均不是首版验收条件。第 13 章给出分期和完成标准。

**边界**：Grayling 决定变体及 AI 配置，不管理服务发现、实例健康或网关路由；不充当通用 APM、数仓或模型推理服务。网关流量切换属于可选集成。Nacos 兼容只覆盖配置传输，不等于现有应用零改造：业务仍须调用求值接口并正确记录曝光。

## 2. 仓库与依赖事实

| 依赖 | 已核对的能力 | 必须尊重的限制 |
|---|---|---|
| gonacos | `server.New(...).Services()` 可直接取得 Config、AI、Auth 等服务；`Config.Publish/Get/List/HistoryList` 提供配置与历史；AI prompt 有 `GetPromptVersion`、`DownloadPromptVersion` | `Config.SetPushFunc`/`SetSyncFunc` 是单回调，`server.New` 已装配，不能再覆盖；配置变更订阅经 Nacos gRPC 流；Auth 的 `Authorize` 未在普通配置读路径强制执行；AI 资源存储以全局 ID 索引，没有与 Config 相同的 namespace 字段 |

## 3. 组件、职责与请求链路

```text
管理端/CI ──Admin API──> Grayling 控制面 ──Config.Publish──> gonacos Config
                              │                            │
                              ├──发布校验/授权/审计          └──Nacos gRPC 通知
                              └──实验/指标库 (PostgreSQL)          │
应用后端 ──Go SDK 本地求值<──版本化配置快照<──SDK API/同步器<───┘
Web 客户端──受限配置或远程求值<────Grayling SDK API/代理
事件采集 ──去重/持久化──> 聚合与统计报告
AI 应用 ──求值结果中的版本引用──>授权的资源解析器──>任务级快照
```

- **热路径**：服务端 SDK 在本地已验证快照上求值，无每请求网络调用；冷启动取快照失败时返回调用方默认值/安全变体，并报告原因。Grayling proxy 可选，用于浏览器受限快照、远程求值、SSE 转发；不要求全部应用请求经过 proxy。
- **发布路径**：管理员提交草稿 → 校验 schema、引用、权限与限额 → 产生不可变 revision → `Config.Publish` → SDK 拉取并原子替换已校验快照。发布确认以目标 revision 可读为准，推送只作提速信号。
- **推送路径**：SDK/proxy 可用 Nacos 客户端按明确的 `(namespace, group, dataId)` 订阅，收到通知后重新 `GetConfig`；Grayling 对外 SSE 发送 revision/失效通知，客户端重拉完整快照。SSE 断线按 Last-Event-ID 尝试续传；若日志已过期则全量重同步。周期轮询兜底，避免通知丢失导致永久陈旧。
- **枚举问题**：Nacos `ListenConfig` 需要已知 dataId。Grayling 维护每工作空间/环境的版本化 manifest，列出可见 flag 的 key/revision；SDK 先订阅 manifest 再拉取具体配置，不依赖服务端通配符或前缀订阅。manifest 发布在 flag 写入成功后，删除用 tombstone；客户端从缺失项清缓存。
- **集群**：gonacos Redis 同步只覆盖其自身状态。Grayling 的审批、实验定义、发布任务、事件和审计写入 PostgreSQL；以事务及幂等任务处理。Config 与 PostgreSQL 没有跨库原子事务，发布状态记录目标 revision 并靠重试/对账收敛；不报告“已生效”直到读回验证。

首版拓扑为 Grayling server + 同进程 gonacos + PostgreSQL；开发模式可用 gonacos 内嵌 Redis，生产集群使用外部 Redis。配置存储与指标存储分别备份；`Server.Snapshot/Restore` 不覆盖 PostgreSQL。`WithRoot` 指向 gonacos 契约根目录，`WithDataDir` 只控制内嵌 Redis dump；应在镜像构建时固定契约文件路径并验证，不能依赖进程 CWD。

## 4. 网关协同

默认在应用内求值，Traefik 只做常规路由。如须把用户稳定送往不同服务版本，采用 **Traefik ≥3.6 multi-layer routing**（PR #12130，2025-10 合并）：父 router 匹配后先执行 middleware，子 router 再按被修改的请求做最终路由，从而让网关层求值可行而无需 fork Traefik。完整链路与配置见 [traefik-grayling-architecture](traefik-grayling-architecture.md)。

1. **父 router + ForwardAuth 求值 + 子 router 分流**（首选）：父 router（无 service，独占 entryPoints/tls）挂两级 middleware——先以 headers middleware 将外部自带的 `X-Grayling-Variant` 置空剥离（防伪造），再经 forwardAuth 调用 Grayling 求值服务（即 P4 远程评估 proxy）按 `bucketingKey` 求值，经 `authResponseHeaders` 回写 `X-Grayling-Variant`/`X-Grayling-Flag-Key`；子 router 以 `Header(...)` 规则分流到各版本 service，另设兜底子 router。求值服务内部错误须 fail-open 返回默认变体，避免网关 5xx；曝光在决策点集中记录。
2. **独立前置代理先求值**：在 Traefik 之前由入口代理写入受信变体 header，router 按 header 匹配。适用于无法使用 forwardAuth 的场景；同样要求边界剥离外部同名 header。

求值服务（grayling-proxy）另支持**按 client IP 灰度**：从可信代理链推导客户端真实 IP（配置 `-trusted-proxy-cidrs`，或环境变量 `GRAYLING_TRUSTED_PROXY_CIDRS`；从连接对端出发仅在可信 CIDR 内逐跳回退 X-Forwarded-For，不受信段一律丢弃，防客户端自报 IP 自选灰度组；未配置时不信任任何 XFF、只用 RemoteAddr，现网行为不变），以保留属性名 `client_ip` 注入 forwardAuth 与 `/sdk/eval` 中继两条服务端求值路径的求值上下文（中继路径上调用方显式传入的同名属性优先），供 `in_cidr` 定向或按 IP 分桶使用；链路、安全语义与实验慎用/隐私提示见 [traefik-grayling-architecture](traefik-grayling-architecture.md)"按 client IP 灰度"节。

约束：multi-layer routing 仅支持 file、KV（Consul/etcd/Redis/ZooKeeper）与 Kubernetes CRD（IngressRoute）provider，Docker label / K8s Ingress / Gateway API 不支持，管理面生成 router 配置时按此选择目标并校验层级规则（中间 router 无 service、叶子必须有 service）。比例调整只改 Grayling 分桶参数，不改 Traefik 动态配置，故无 provider 传播延迟；增删变体才变更 router。local plugin（Yaegi）路线放弃，ForwardAuth 为标准 middleware，无解释器兼容性问题。Traefik HTTP/Redis provider 改 weighted service 权重仍只可用于无身份要求的容量验证，不能等同实验用户稳定分组；cookie sticky 不能替代跨 SDK 的同一 `bucketingKey` 分组。[Router 顺序](https://doc.traefik.io/traefik/reference/routing-configuration/http/routing/rules-and-priority/)、[provider](https://doc.traefik.io/traefik/reference/routing-configuration/dynamic-configuration-methods/)、[multi-layer routing](https://doc.traefik.io/traefik/reference/routing-configuration/http/routing/multi-layer-routing/)、[PR #12130](https://github.com/traefik/traefik/pull/12130)。

## 5. 存储与版本化数据模型

### 5.1 标识与所有权

所有管理对象以 `(workspace_id, environment_id, object_type, key)` 唯一。gonacos Config 的 namespace 对应工作空间**与环境的组合映射 ID**，group 固定为 `GRAYLING_FLAGS`。每次发布把完整内容写入不可覆盖的 `grayling.flag.<key>.r<revision>` dataId，再更新单独的 `grayling.manifest`，由 manifest 指向各 flag 的确定 dataId、revision 和 hash。发布前读回校验；旧版本保留到 SDK 最大陈旧期及回滚窗口之后，按配额清理。映射和 key 规范由 Grayling 持久化，不把用户提供的字符串直接拼进底座 ID。环境之间不共用可变配置。

gonacos AI `Resource` 没有 namespace 字段，所以不能凭工作空间 namespace 隔离 AI 内容。Grayling 维护 `(workspace, environment, resource_type, logical_id) → physical_id/owner` 索引；physical ID 必须唯一且由服务端生成，所有 AI 读写走 Grayling 授权入口。若无法对某类 gonacos AI API 保证隔离，就先禁用该类跨租户托管，改由外部资源适配器提供。禁止把 gonacos 原始 HTTP/gRPC 服务直接暴露给租户。

### 5.2 Flag、规则、快照

```yaml
schemaVersion: 1
key: checkout-router
type: json
disable: false
version: "17"                # Grayling 发布 revision
bucketing: {algorithm: grayling-fnv1a-10000-v1, unit: user_id, salt: "checkout-v1"}
variations:
  control: {modelRef: {provider: qwen, model: qwen-max}}
  candidate: {modelRef: {provider: anthropic, model: approved-model-id}}
defaultRule: {variation: control}
targeting:
  - name: internal
    constraints: [{field: tenant, op: in, values: [acme, globex]}]
    variation: candidate
  - name: public-ramp
    percentage: {control: 90, candidate: 10}
```

这是 **Grayling DSL**，不是可直接交给 `flag.InternalFlag` 的 gff 文档。导入器只支持明确列出的 gff 字段（`variations`、`disable`、`targeting[].query`、`defaultRule`、`percentage` 等），严格解析并报告不支持字段；禁止静默丢字段。可提供 `legacy-gff-v1` 兼容模式继续按 gff 原算法求值旧实验；切换至 Grayling 算法须新建实验 epoch，记录迁移影响，不能承诺原用户分配保持不变。`evaluation.Evaluate` 仅用于 legacy 模式或对照；Grayling 原生固定桶路径自行产出 reason/detail。

发布快照含 schemaVersion、workspace/environment、manifest revision、flag/segment 依赖的确定版本、内容 hash、生成时间与签名/完整性校验。读者按 manifest 下载全部引用并验证 hash 后才原子替换，不能把不同 manifest revision 的部分 flag 拼装。配置写入与 manifest 发布使用幂等 revision；SDK 比对 revision/hash，忽略旧通知。未取得新快照时继续使用最后一个有效快照并标记 stale，超出可配置最大陈旧时间改用安全默认值；kill switch 对离线节点只能保证在推送/轮询恢复后生效，必须给出最大陈旧窗口。

规则按列表顺序匹配；优先判断禁用/紧急关闭，再校验 context 和实验状态，再匹配定向规则，最后默认规则。定向条件只允许注册字段及有界操作符（等值、集合、数值、时间、正则、CIDR、semver）；正则编译、执行成本及输入长度受限。segment 有版本与工作空间边界，循环引用拒绝。对相同发布 revision/context 的求值结果必须确定；错误时返回显式 default、reason/error，不静默随机分组。

### 5.3 实验与发布状态

实验记录：`experiment_id`、workspace/environment、flag/revision、`epoch`、随机化单元、互斥层、资格规则、变体及比例、主指标、护栏、分析窗口、假设、MDE、alpha/power、预注册分析方法、起止时间与状态。状态机为 Draft → Reviewed → Scheduled/Running → Paused/Stopped → Analyzed → Archived；变更随机化单元、指标口径、比例或资源绑定会创建新 epoch，不能覆盖历史实验。

发布记录：草稿、审核、当前 revision、计划步骤、观察窗、暂停/回滚原因、操作人及关联审计。回滚是发布一个**新 manifest revision**，指向经验证且仍保留的旧配置版本；历史记录不能作为原子回滚 API 的替代品。自动推进只在观测窗口、数据完整性、最小样本及全部护栏均满足时执行；统计不可用、SRM、推送异常或 judge 低可信时暂停，不自动宣称成功。

## 6. 分桶、粘性与互斥

Grayling 原生算法规范 `grayling-fnv1a-10000-v1`：将 UTF-8 编码的长度前缀字段 `(workspace, environment, experiment_or_flag_key, epoch, salt, unit_value, purpose)` 依序拼接，做 FNV-1a 64-bit，取 `% 10000` 得到 `0..9999`。`purpose=eligibility` 与 `purpose=variant` 分离；百分比换算为整数桶，校验总和恰为 10000，变体按显式稳定顺序分配。规范同时固定缺失值处理、Unicode 编码和跨语言黄金向量。固定模只保证 hash 坐标不变；改变比例会移动区间边界，任意多臂重配可能使部分用户换臂。需要跨比例更改保持既有分配时，应使用下述持久 sticky 记录或新建 epoch，不能承诺“固定模即可绝对 sticky”。

随机化单元必须是经过认证或可信生成的稳定 ID；没有 ID 时返回默认变体并报告 `MISSING_BUCKET_KEY`，不生成每次请求的新随机数。保留字段 `client_ip`（grayling-proxy 从可信代理链推导注入，§4）允许作为分桶单元且校验**不阻断**，但**实验慎用**：IP 随 NAT、动态分配与代理链变化漂移，单元不稳定会破坏粘性与曝光归因，只宜用于无身份要求的流量/容量灰度；实验级分桶应使用认证稳定 ID。匿名用户可由服务端签名 cookie 提供稳定 ID，并在登录时定义是否合并；会话实验使用 conversation ID。互斥层先用独立 seed 划分不重叠桶区间，再在命中实验内分臂；跨层同时运行的实验可能存在交互效应，应采用因子设计或在报告中明确限制。

实验资格筛选每次仍须通过安全与受众规则；sticky assignment 只在同一 experiment/epoch、相同随机化单元且仍符合资格时使用。持久 sticky 记录只在需要跨比例更改保持既有分配时启用，键含 workspace/environment/epoch/单元哈希、变体、时间及版本，TTL 至实验结束加归因窗口；Redis 丢失会影响分配，需监测并可重建。纯确定性分桶不要求每用户缓存。保留旧分配与严格维持新目标比例可能冲突；启用 sticky 后应统计实际入组概率和比例，比例改变或资格改变时先模拟影响，必要时新建 epoch，不能把预设比例直接用于 SRM 期望值。修改盐、算法版本或随机化单元必须建新 epoch，并在统计上作为新实验处理。

## 7. AI 资源绑定与 Agent 运行语义

变体引用应指向 `(workspace, type, physical_id, immutable_version, digest)`，发布前验证所有权、版本存在、可用状态、内容摘要和运行权限。`modelRef` 是 Grayling 适配器维护的 provider/model/参数白名单，不假定 gonacos 托管模型版本。MCP、pipeline 等资源只有在对应适配器支持不可变版本读取和授权校验后才可发布；不以字符串 `name@v1` 代替验证。

`BindPromptLabel` 只是给 prompt 资源加 label，不能证明 label 唯一指向某个历史版本，也不能实现原子“切 label 回滚”。默认发布时把 label 解析为明确的 prompt version 与 digest，快照中固定该版本；回滚重发绑定旧版本的新 flag revision。资源更新不改变已有实验快照。禁止把敏感 prompt 内容或供应商凭证发往浏览器，前端仅收受限变体值或调用远程评估。

Agent 会话/任务开始时评估一次，冻结 flag revision、各资源版本、解析顺序及参数，随任务上下文传递；长任务收到新配置仅影响后续任务。紧急安全撤销需另设可即时阻断的执行前校验，不依赖普通快照。多 Agent 工作流若要整体切换，用一个工作流级变体绑定完整资源图；若各层独立实验，要显式记录组合曝光，并设计交互效应分析，不把“分层”误作天然正交。

## 8. 分发、SDK 与 OpenFeature

首版 Go SDK：全量快照拉取、ETag/304、订阅失效通知、轮询重同步、原子缓存、离线兜底、求值详情、批量曝光上报、超时/限流与观测。`GET /api/v1/sdk/config` 只按 token 的 workspace/environment 发受限配置，不接受 query 参数越权选择租户；delta 协议待有可回放事件日志后再做。浏览器首版优先远程求值或仅下发公开 flag 投影，不能暴露内部规则、segments 和 AI 内容。

现有 Nacos SDK 可用于拉取**已知** dataId 和 `ListenConfig`，但它拿到的是原始配置，不会执行 Grayling 评估，也不能自动发现新 flag；须先读取 manifest。Java/Python 若没有已验证的本地评估实现，可先调用远程评估，不能宣称 nacos SDK 接入“零业务改造”。多语言本地 SDK 需共享黄金向量与类型/错误语义契约。

OpenFeature Provider 实现布尔、字符串、数值、对象求值，映射 `targetingKey` 到稳定单元并返回 variant、reason、error code；缺少必需 ID 时按规范返回调用方 default 与错误。OpenFeature 的 resolution details **支持 reason**，不能说 Provider 无法暴露原因。曝光采集可由 Grayling Provider 内部事件钩子或原生 SDK 提供，但应遵循“真正使用/进入实验才曝光”，不把预取配置计为曝光。[OpenFeature Provider 规范](https://openfeature.dev/specification/sections/providers/)。

## 9. 安全与隔离

- 管理 API、SDK API、采集 API 使用不同凭证和受众；每次请求先鉴权，再从凭证确定 workspace/environment，再做对象级授权。管理角色最小为 owner、publisher、analyst、viewer；发布和读取原始 AI 内容单独授权。审批人不能批准自己的高风险变更。
- gonacos 当前常规配置读路径允许匿名访问，故仅通过进程内服务接口使用，底座 HTTP/gRPC 监听限定 loopback/私网并用网络策略拒绝租户直连；生产验证未授权直连被拒。`Auth.Authorize` 数据模型可借鉴，Grayling 必须自己执行策略。跨工作空间资源引用默认拒绝，显式共享也需双边授权和版本冻结。
- SDK 配置是公开/受限投影；管理密钥、provider API key、敏感 prompt、审计详情绝不下发浏览器。TLS、密钥轮换、存储加密、日志脱敏与审计保留期在部署基线中定义。
- 采集端限制事件大小、速率、时间偏移和维度基数；事件 ID 去重；PII 只用带租户范围的伪名化随机化单元，原始 prompt/response 不进入普通指标事件。judge 样本单独授权、脱敏、按保留期删除。
- `/api/v1/signals` 等自动动作采用签名或专用服务令牌、幂等键、冷却时间、人工可暂停开关和审计。任何信号不得绕过发布权限与安全默认值。

## 10. 实验事件、指标与统计

### 10.1 事件契约与归因

曝光事件至少含 `event_id`、workspace/environment、experiment/epoch、flag revision、variant、随机化单元的伪名哈希、session/task ID、事件时间与接收时间、资格及来源；转化事件另含 metric key、数值和归因时间。服务端去重、处理迟到数据、按实验预注册窗口归因。主分析单位是**随机化单元**，不是请求数；请求级成本/延迟需先按随机化单元聚合，避免同一用户多请求造成伪重复。SRM 基于进入实验且真实曝光的单元数，并与预设分配比较；看不到完整曝光时不能用转化数代替。

首版指标仅支持 proportion 与 mean，明确分母、零值、缺失值、单位和方向；成本/延迟护栏可另展示 p95，但 p95 的推断需要保留单元明细或可验证的分布数据，不能仅用 sum/sum_squares 计算。ratio 需每单元分子/分母及交叉乘积；funnel/retention 需有序事件与观察窗口；CUPED 需实验前协变量和实验后结果的同单元配对数据。故不能声称三个聚合量能支持所有指标或 CUPED。

### 10.2 存储与隐私

PostgreSQL 首版保存去重后的受限原始事件（或单元级日聚合）及预计算的 `experiment × epoch × variant × unit × metric` 充分统计；按保留期分区删除，单元 ID 做租户范围内 HMAC，密钥轮换有迁移方案。仅展示汇总，低样本切片抑制。大规模数据量再评估 ClickHouse；不能在无用户级数据时承诺任意维度重算、协变量调整或漏斗计算。数据源故障、事件延迟和丢失率是报告健康条件。

### 10.3 推断与决策

首版固定样本、双臂、单一预注册主指标：均值用 Welch 检验和效应置信区间；比例用适当的二项区间/检验；报告绝对差和相对差（基线接近零时只报绝对差）、样本数、窗口、缺失率、SRM。预先给定 alpha、power、MDE 与最短运行时间。护栏阈值是运营保护规则，和统计显著性分开；自动停止时冻结决策并记录原因。多次查看固定样本 p 值不得据此随时宣称胜利。

后续版本按验证结果加入 ratio、quantile/funnel、CUPED、Holm 多重比较、贝叶斯或序贯方法。每种方法必须写明先验/检验家族、可选停止规则、缺失处理、与指标类型的适用边界，并用模拟数据检验覆盖率、I 型错误、功效及 SRM 灵敏度。Bandit 是探索优化策略，不与固定比例 A/B 共用传统 p 值结论；分配概率及时间必须逐次记录，使用相应估计方法。不能将“默认 Bayesian”和“固定频率派 95% CI”混成同一决策规则。

### 10.4 LLM-as-judge

judge 通过独立异步任务按预注册采样概率抽样，记录 rubric/judge 模型/版本、输入摘要、评分、失败率和人工校准集结果。位置随机化用于成对比较；长度差、模型自评偏差和安全数据处理都应在报告中披露。分层采样或动态采样须记录每条样本的入样概率，统计时按设计加权；不能仅把不同采样率的评分直接平均。校准不达标、样本小或判官漂移时质量指标只作诊断，不驱动自动放量或回滚。

## 11. API、控制台与运维

| API | 首版职责 | 保护 |
|---|---|---|
| `/api/v1/admin/**` | flag/segment/实验/发布草稿、校验、审批、历史、调试 | 管理身份 + 对象级 RBAC + 乐观锁 revision |
| `/api/v1/sdk/config`、`/api/v1/sdk/eval` | 已授权快照、远程求值 | 限环境 client token + 速率限制 |
| `/api/v1/sdk/stream` | revision 失效通知 | 同环境 token + 断线重同步 |
| `/api/v1/collect` | 曝光/指标事件批量接收 | 独立采集令牌 + 幂等事件 ID |

控制台首版提供工作空间/环境、flag 编辑与校验、发布审查、评估调试、实验状态/结果、审计记录；高级统计、跨语言 SDK 和 AI 资源管理按阶段开放。评估调试器默认不写曝光。

可观测性覆盖 SDK 快照年龄、版本分布、推送到拉取延迟、求值延迟与错误、发布对账积压、事件接收/去重/丢弃、SRM 与数据延迟。备份须联合验证 gonacos Snapshot、PostgreSQL 和密钥，按同一恢复点做演练；恢复后重建 manifest/SDK 快照并核对 revision。资源限额按工作空间配置，至少限制 flag 数、单 flag 大小、规则/segment 深度、SDK 快照大小、SSE 连接数、事件速率和存储保留期；默认值由压测给出，不能凭竞品数字直接设为生产承诺。

## 12. 依赖与兼容性验收前置

1. 固定 gonacos commit、Go 工具链和 gff core 版本，做最小编译/启动原型；检查 `WithRoot` 契约加载、`Config.Publish/Get/List/HistoryList`、AI 指定版本读取、Snapshot/Restore。
2. 用真实 Nacos 客户端验证已知 dataId 的配置订阅、跨节点通知、断连重连、丢通知后轮询恢复；确认不存在可依赖的“前缀订阅”。
3. 建立 gff 原生配置导入对照集：明确支持字段、未知字段报错、legacy 求值结果；Grayling 原生算法单独建立跨语言黄金向量，迁移实验记录重分配比例。
4. 用 Traefik ≥3.6 固定版本验证 multi-layer routing 链路（父 router ForwardAuth 求值 + 子 router header 分流）与 weighted service 更新；local plugin 路线已放弃，不再做原型。
5. 复核 gonacos 许可文件与第三方分发内容，并验证 AI 资源多租户隔离方案及生产网络策略；未通过的安全项不得对外提供多租户生产服务。

## 14. 关键风险与权衡

| 风险 | 影响与应对 |
|---|---|
| gonacos 授权和 AI 全局资源 ID | namespace 不能自动保护原始 AI 内容；对外隔离底座端口、Grayling 自建对象级授权和所有权索引，P0 做越权验证 |
| gonacos 推送钩子为单回调 | 不能覆盖 `SetPushFunc`/`SetSyncFunc`；客户端订阅 + 拉取 + 轮询兜底，后续如需内进程通知应先在上游设计多播接口 |
| gff 算法与 Grayling 固定桶不一致 | 原生模式不直接调用 `Evaluate`；legacy/原生模式分别测试，实验迁移开新 epoch |
| 跨存储一致性 | Config 与 PostgreSQL 无分布式事务；幂等 revision、发布读回、状态对账、审计补偿 |
| 统计偏差 | 曝光漏报、SRM、重复请求、可选停止、混合 epoch 或动态采样会误导结论；预注册口径并禁止不健康报告自动决策 |
| AI 资源与会话漂移 | 资源引用固定版本/摘要，任务冻结快照；紧急撤销单独阻断 |
| 多语言与隐私 | 本地评估移植成本高；优先 Go 与远程评估，浏览器只给受限数据；契约和伪名化单元强制验证 |
| Traefik 集成 | 普通 middleware 时序问题已由 ≥3.6 multi-layer routing 解决，但引入新约束：求值服务（forwardAuth）不可用会拒绝请求，须高可用部署并 fail-open；provider 仅限 file/KV/IngressRoute；版本须锁定 ≥3.6 并端到端验证 |
| 依赖许可与升级 | gonacos 当前固定版本含 Apache-2.0 LICENSE/NOTICE；升级需重审许可范围并重跑兼容/安全/性能测试 |

## 15. 非目标

首版不做服务拓扑管理、原生网关流量调度、全部竞品功能或 SDK、通用数仓、通用 APM、移动端 SDK、内置 LLM 推理。上述能力若未来进入路线图，必须有单独接口、资源预算和验收门槛。
