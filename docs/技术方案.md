# GoLab 技术方案

## 1. 目标

新建 `golab` 独立 Go 项目，构建面向 **AI 应用的灰度发布与 A/B 实验平台**。

- **功能对标**：完整覆盖 Unleash 与 GrowthBook 的功能集 —— feature flag 类型体系、activation strategy 全集、约束操作符全集、segments、多变量实验、渐进式发布、变更审批、RBAC/SSO、审计、SDK 全集与 OpenFeature 兼容。
- **引擎复用**：复用 go-feature-flag 的**评估内核与 flag 数据模型**；DSL 在其字段基础上扩展私有字段，分桶改用固定模方案（见 7.1 / 8.2）。
- **底座复用**：控制面存储、变更推送、权限、集群、AI 资源版本管理基于 gonacos，不重复建设注册中心与配置中心能力。
- **AI 差异化**：prompt / model / skill / AgentSpec / MCP / pipeline 的版本灰度，以及 token 成本、延迟、质量三维指标与 LLM-as-judge 在线评估。

一句话：**Unleash 的功能广度 + GrowthBook 的统计深度 + AI 资源的原生灰度能力**。

## 2. 背景与问题

AI 应用的发布形态与传统服务存在本质差异：

| 维度 | 传统服务 | AI 应用 |
|---|---|---|
| 行为决定因素 | 代码分支 | prompt / 模型 / 参数 / 检索策略 |
| 变更方式 | 重新部署 | 改配置，无需部署 |
| 影响预判 | 可静态分析 | 只能靠线上指标观测 |
| 成本结构 | CPU / 内存 | token 成本，与流量线性相关 |
| 质量度量 | 错误率、延迟 | 幻觉率、相关性、用户采纳率 |

传统 flag 平台灰度的是**代码路径**，无法覆盖 AI 资源的版本灰度：

- 同一个功能有多个 prompt 版本，需要按流量比例分发并对比效果。
- 模型供应商与版本需要灰度切换，且必须同时观测成本与质量。
- AgentSpec / Skill 组合变更的影响面比代码变更更难预判。
- 实验结论需要统计显著性支撑，而非拍脑袋。

现有三方方案各有缺口：

- **Unleash**：flag 能力完整，但无 AI 资源概念，统计能力弱。
- **GrowthBook**：统计引擎是强项，但同样面向代码 flag，且后端为 Node + MongoDB，无法复用 gonacos 生态。
- **go-feature-flag**：评估引擎与配置模型优秀，但只是 SDK + relay，没有控制面、实验分析、权限体系。
- **gonacos**：有完整的 AI 资源版本与生命周期管理，但没有流量分配、定向规则、实验分组与统计检验。

**golab 的立足点**：在 gonacos 的资源版本体系之上，加一层评估引擎与实验分析层。

## 3. 定位：三层职责

```text
┌─────────────────────────────────────────────────────────────┐
│  分析层   指标采集 · 统计检验 · 实验报告 · LLM-as-judge        │  golab 自建
├─────────────────────────────────────────────────────────────┤
│  决策层   评估引擎 · 定向规则 · 流量分桶 · 实验分组 · 审批      │  golab 自建
│           (评估算法可复用 go-feature-flag 模型)                │
├─────────────────────────────────────────────────────────────┤
│  资源层   AI 资源版本 · 配置存储 · 变更推送 · 权限 · 集群       │  gonacos 复用
└─────────────────────────────────────────────────────────────┘
```

**资源层**（gonacos 提供，golab 直接 import）：

- 配置存储与历史版本（`pkg/config`）
- 底座级 IP 灰度（`GrayRequest.GrayRule`）
- 变更产生（gonacos 内部 `PushService`，gRPC-only）
- 集群同步（gonacos 内部 Redis pub/sub）
- 命名空间隔离（`pkg/namespace`）→ 数据隔离（**非鉴权隔离**）
- 用户 / 角色 / 权限的**数据模型**（`pkg/auth`）—— 其细粒度鉴权无 enforcement，授权执行层须自建（见 11.3）
- AI 资源版本管理（`pkg/ai`）→ prompt / skill / agentspec / MCP / A2A / pipeline

**决策层**（golab 自建）：

- flag 与实验的统一评估引擎
- 定向规则、约束操作符、segments
- 哈希分桶（固定模 10000）与 sticky bucketing
- 渐进式发布调度（定时/自动推进）
- 实验分组与互斥

**分析层**（golab 自建）：

- 指标定义与事件采集
- 频率派 / 贝叶斯 / 序贯检验
- CUPED 方差缩减、SRM 检查
- LLM-as-judge 评估管线

## 4. 与既有项目的关系

### 4.1 gonacos：底座

golab 作为**同进程嵌入** gonacos 的库使用，而非跨进程调用：

```go
srv, err := server.New(server.WithAddr(":8848"))
if err != nil { ... }
bundle := srv.Services()          // *app.ServiceBundle

bundle.Config.Publish(...)                        // flag 存储
bundle.AI.GetPrompt(...)                          // AI 资源读取
bundle.Auth.Authorize(claims, res, action)        // 仅复用其调用形态，拦截在 golab 中间件（见 11.3）
// 注意：变更推送由 gonacos PushService 内部处理，勿调用 SetPushFunc（见 11.2 / 16.1）
```

gonacos 底座能力与 golab 的可用边界（经编译与运行时实测）：

| 能力 | gonacos 接口 | golab 用途 |
|---|---|---|
| flag 存储 | `Config.Publish/Get/List` | flag 定义与变体内容 |
| 历史版本 | `Config.HistoryList/HistoryDetail/PreviousHistory` | flag 变更审计与回滚 |
| 灰度规则 | `Config.PublishGray` + `GrayRequest.GrayRule` | 底座级 IP 灰度（实测仅支持 `betaIps` 精确匹配，职责边界见 9.4） |
| 变更推送 | gonacos 内部 `PushService`（gRPC-only，见 11.2） | golab **不可**调用 `SetPushFunc`（见 16.1） |
| 集群同步 | gonacos 内部 Redis pub/sub | golab **不可**调用 `SetSyncFunc` |
| 多租户 | `Namespace.*` | 工作空间隔离 |
| 权限 | `Auth.*` | 仅数据模型与调用形态；RBAC 拦截由 golab 自建（见 11.3） |
| AI 资源 | `AI.CreatePromptDraft/.../OnlinePrompt` | 灰度对象来源 |
| 资源分组 | `AI.BindPromptLabel` | 版本标签与灰度分组 |
| 快照备份 | `Server.Snapshot/Restore` | 全量备份 |

**集成注意事项**（实测发现）：

- `api/openapi/upstream` 契约路径基于**进程 CWD** 解析（默认 `"."`），嵌入时若工作目录不含该路径，未实现的 501 stub 不会注册。golab 须通过 **`server.WithRoot(<gomod 根>)`** 显式指定（注意：`WithDataDir` 是内嵌 Redis 的磁盘 dump 目录，与此无关）。
- gonacos 当前**无 LICENSE 文件**。golab 若要公开发布，需先明确 gonacos 的许可协议或改为松耦合（跨进程 SDK）以规避许可传染。

### 4.2 go-feature-flag：评估内核

复用其**评估内核**（`modules/core` 可作为独立依赖，已实测 `go get modules/core@v0.7.2` 即可构建），而非整套 runtime：

- 评估入口 `evaluation.Evaluate[T]`
- flag 结构体 `flag.InternalFlag` 与四种 rollout 策略（官方口径：**Percentage** / Progressive / Experimentation / Scheduled）—— 注意其**层级不同**：`Percentage` 与 `ProgressiveRollout` 是 **rule 级**字段（`Rule.Percentages` / `Rule.ProgressiveRollout`），`Experimentation` 与 `Scheduled` 在 **flag 级**（`Rollout` 结构体）。其中 Percentage 正是 7.1 与 9.4 实际使用的机制
- 分桶与变体分配算法（**fnv32a + mod-N**，注意其变模特性，见 8.2）
- 评估原因枚举与 `resolution_detail` 追踪

**配置格式的迁移方向是单向的**：gff 配置可导入 golab；但 golab 的 flag DSL 含私有扩展字段（`type` / `contextFields` / `aiBinding`），**不能被 gff 消费**。详见 7.1。

**已知依赖细节**：`modules/core` 的 go.mod 含 `replace github.com/nikunjy/rules => ...`，而 replace 指令在依赖模块中会被 Go **忽略** —— golab 实际解析到上游 `nikunjy/rules` 而非 gff 自测用的 fork。当前可编译，但须记入风险（见 16.1）。

### 4.3 golab 自建的独有部分

- 控制面（Web 控制台 + 管理 API）
- 实验管理与统计引擎
- 指标采集与 LLM-as-judge
- AI 资源与流量的绑定关系
- 渐进式发布调度器
- 审批流与变更请求

### 5.2 请求路径

**评估路径**（热路径，延迟敏感）：

```text
应用 → golab-proxy(本地缓存命中) → 返回变体       [~微秒级]
     └→ 缓存未命中 → golab-server /sdk/eval → 分桶计算
```

**管理路径**（冷路径）：

```text
控制台 → Admin API → 校验 → gonacos Config.Publish
                              ↓ gonacos 内部 PushService（golab 不注册钩子）
                        gRPC BiRequestStream
                              ↓
                        golab-proxy → SSE → 浏览器 / 边缘 SDK
```

**指标路径**（异步）：

```text
SDK 上报事件 → /collect → 缓冲 → 批写入指标存储 → 统计引擎
```

### 5.3 部署拓扑

| 形态 | 组件 | 适用 |
|---|---|---|
| 单机嵌入 | golab-server + gonacos(同进程, 内嵌 miniredis) | 开发、小规模、边缘 |
| 标准集群 | golab-server ×N + gonacos ×N + Redis + PostgreSQL | 生产 |
| 边缘分发 | golab-proxy ×N(CDN/就近) + 中心控制面 | 全球化、低延迟 |


`pkg/gonacos` 是唯一的底座耦合点 —— 其余模块只依赖 `pkg/gonacos` 暴露的接口，便于未来替换底座而不影响核心逻辑。

## 6. 功能对标矩阵

### 6.1 对标范围

对标三个项目，覆盖其**功能全集**（含付费功能，golab 全部开源实现）：

| 项目 | 对标重点 | 其缺口 |
|---|---|---|
| **Unleash** | flag 类型体系、strategy 全集、constraints、segments、change requests、RBAC | 无 AI 资源概念；统计能力弱 |
| **GrowthBook** | 统计引擎、指标体系、health checks、bandits、ramp schedules | 无 AI 资源概念；核心统计引擎是独立 Python 库；大量功能收费 |
| **go-feature-flag** | 评估内核、flag DSL、retriever/exporter 框架 | 无控制面、无实验分析、无权限 |

### 6.2 Flag 模型与评估

| 能力 | Unleash | GrowthBook | go-feature-flag | golab |
|---|---|---|---|---|
| flag 语义类型 | **6 种**：release / experiment / operational / kill-switch / permission / sunset（各有预期存活期） | 无显式类型（按用途约定） | 无显式类型 | 四类语义 + 四值类型 |
| 值类型 | boolean（多值靠 variants） | boolean / string / number / json | 任意 JSON | 两者兼容 |
| 多变量 | strategy variants（权重 0–100，总和须为 100，支持 Variable/Fixed 两种权重） | variations（weights 和须≈1，否则退化均分） | variations + 百分比 | 兼容两种权重模型 |
| 变体 payload | string / json / csv / number | 值即 payload | 值即 payload | 兼容 |
| 规则类型 | 策略 + 约束（策略间 OR，约束间 AND） | force / rollout / experiment / bandit（有序，先匹配者胜） | targeting + defaultRule | 兼容两者：有序规则 + 策略组合 |
| 评估原因 | 有（SDK 返回 reason） | 有（`FeatureResult.source` / `ruleId`） | 有（resolution_detail / resolution_reason） | 全量透出到控制台调试器 |
| 哈希算法 | MurmurHash3，key 为 `groupId:id`，结果 `1..normalizer` | fnv32a 双重散列，**固定模 10000**（v1 为模 1000，有并行实验偏差） | **fnv32a + mod-N（变模）**：`Hash(flagName+bucketingKey) % maxPercentage` | **固定模 10000**，详见 8.2 |
| flag 依赖 | **Feature dependencies**（父 flag + 期望值 + 变体，按环境独立解析） | **Prerequisites**（顶层布尔前置 + inline 条件前置；支持 Schrödinger 型运行时求值） | 无 | 自建，对标两者 |
| Sticky bucketing | 继承策略 stickiness，改 `groupId` 重新分配 | 支持（主/次属性 + bucketVersion + minBucketVersion） | 无 | 自建，语义对标 GrowthBook |

### 6.3 定向与约束

| 能力 | Unleash | GrowthBook | go-feature-flag | golab |
|---|---|---|---|---|
| 条件语法 | context field + operator + values | MongoDB 风格查询（`$eq/$in/$regex/$elemMatch/...`） | query 字符串（nikunjy 池） | 统一 DSL，兼容 gff query，补齐 GrowthBook 算子 |
| 操作符 | **19 个**（代码口径；官方文档页仅列出 17 个，`REGEX` 与 `IN_CIDR` 未在该页文档化）：IN/NOT_IN、STR_ENDS_WITH/STARTS_WITH/CONTAINS、NUM_EQ/GT/GTE/LT/LTE、DATE_AFTER/BEFORE、SEMVER_EQ/GT/GTE/LT/LTE、REGEX、**IN_CIDR**；统一 `inverted` 取反 + `caseInsensitive` 选项 | `$eq/$ne/$lt/$lte/$gt/$gte/$regex/$in/$nin/$all/$elemMatch/$size/$exists/$type/$not/$and/$or/$nor`、SemVer `$veq/$vlt/$vgt`、`$inGroup` | 支持 eq/neq/gt/lt/in/not_in/contains/starts_with/ends_with/regex | 三者的并集 + AI 专用算子 |
| 可复用定向 | **Segments**（约束片段，空 segment 恒真，单策略最多 5 个，实例最多 300） | **Saved Groups**（Condition Group / ID List，上限 1 MB，支持引用传递） | 无 | 自建，对标两者 |
| 上下文字段 | 内置 + 自定义，支持类型与隐私（Secure String 传 SDK 前哈希） | Attributes 8 种类型 + Constrained List + 数据类型可原地修改 | context（key + custom） | 内置 + 自定义 + AI 上下文 |
| 跨项目定向 | 有（release templates 共享策略） | 有（targetingProjects + 审批约束） | 无 | 有（对标） |

### 6.4 灰度与渐进发布

| 能力 | Unleash | GrowthBook | go-feature-flag | golab |
|---|---|---|---|---|
| 灰度策略 | **8 种**：`default` / `flexibleRollout` / `userWithId` / `remoteAddress`（含 CIDR）/ `applicationHostname` / `gradualRolloutUserId` / `gradualRolloutSessionId` / `gradualRolloutRandom`，外加 custom strategies（参数类型 string / percentage / list / number / boolean） | 无策略概念，用 rule 类型表达（force / rollout / experiment / bandit） | query + rollout 百分比 | 覆盖全部语义 |
| 渐进放量 | Gradual rollout（按百分比，用户稳定） | Ramp Schedules（1% → 5% → 10% → 25% → 50% → 100%，可 Hold for 时长/审批/最小样本） | Progressive rollout（按**日期**在 initial/end 间推进） | 自建：时间驱动 + **指标驱动** |
| 定时发布 | Scheduled changes（v5.10，获批后定时应用） | Rule 定时开关 + deferred publish | Scheduled steps（按日期） | 复用 gonacos + 自建调度器 |
| 护栏与自动回滚 | Release templates 三层模型（template / milestone / release plan）+ **Safeguards**（impactMetric + triggerCondition → 关环境或暂停推进） | **Safe Rollout**：guardrail 越界自动回滚并禁用；SRM/无流量/多重曝光可 Hold step / Roll back；阈值恒 0 | 无 | 自建，对标 GrowthBook 并扩展 AI 护栏（成本/质量） |
| Kill switch | flag 类型之一 | 环境级 `enabled` | kill-switch 类型 | 有 |
| 灰度对象 | 代码路径 | 代码路径 | 代码路径 | **代码路径 + AI 资源版本** |

### 6.5 实验设计

| 能力 | Unleash | GrowthBook | go-feature-flag | golab |
|---|---|---|---|---|
| 实验承载 | strategy variants | experiment rule（variations + weights + coverage + trackingCallback） | ExperimentationRollout（仅时间窗，**无权重分配**） | experiment rule，兼容 GrowthBook 语义 |
| 互斥 | Projects + 策略顺序 | **Namespace**（`[id, start, end]`）+ **Filters**（seed + ranges + hashVersion） | 无 | 自建，对标 GrowthBook |
| Holdout | 无 | 有（商业版，5% 默认，靠 prerequisites 绕过流量） | 无 | 自建 |
| Bandits | 无 | Multi-armed（Thompson sampling，每臂保底 1%）+ Contextual（决策树分 leaf，Enterprise beta） | 无 | 自建，对标 GrowthBook |
| Phases | 无 | 有（阶段隔离，不同阶段分别分析） | 无 | 自建 |
| 样本量计算 | 无 | Power Calculator（80% power、MDE、逐周 power 曲线） | 无 | 自建 |
| URL 定向 / Visual Editor | 无 | 有（Simple/Regex 模式；Visual Editor 为 Chrome 扩展，Pro 计划） | 无 | 一期不做 Visual Editor，URL 定向做 |

### 6.6 指标与统计引擎

| 能力 | Unleash | GrowthBook | go-feature-flag | golab |
|---|---|---|---|---|
| 统计引擎 | 无（依赖外部） | **双引擎**：Bayesian（默认）/ Frequentist，org/project 级切换 | 无 | 自建，对标 GrowthBook |

## 7. 核心数据模型

### 7.1 Flag 定义

flag 存储在 gonacos 配置中心，约定 `dataId = golab.flag.<flagKey>`、`group = GOLAB_FLAGS`、`namespace = 工作空间ID`。

**golab DSL 与 gff 格式的关系（关键）**：

golab 的 flag DSL **不是** gff 配置格式的复制 —— 两者字段名与语义均有差异，实测用 gff 的结构体反序列化本文档早期版本的 YAML，`rollout` 块会**被静默丢弃**、`defaultVariation` 丢失导致评估直接失败。必须显式区分：

| 语义 | gff 字段 | golab 字段 | 差异 |
|---|---|---|---|
| 默认变体 | `defaultRule.variation` | `defaultRule.variation` | 采用 gff 字段名 |
| 禁用开关 | `disable: true` | `disable: true` | **语义与 `enabled` 相反**，勿混用 |
| 百分比分配 | `percentage: {control: 70, variantA: 30}`（**map**） | 同 gff | 不是数组形式 |
| 变体表 | `variations: {name: value}` | 同 gff | |
| 定向规则 | `targeting[].query` | 同 gff | |
| 桶序 | **变体名逆字母序**（gff 源码注释自述为 legacy 兼容 HACK） | 同 gff | 按声明顺序实现会与 gff 结果不一致 |

**golab 私有扩展**（gff 解析器不识别，须由 golab 自己的解析层处理）：`type`、`contextFields`、`aiBinding`、`rollout`（渐进发布计划）。

**结构体说明**：可序列化的 gff 结构体是 `flag.InternalFlag`；`flag.Flag` 是**评估接口**（含 `Value(...)` 方法），两者不可混淆。

```yaml
key: checkout-model-router
type: release                    # golab 扩展
disable: false                   # gff 字段（注意不是 enabled，语义相反）
variations:
  control:  { model: "qwen-max",       temperature: 0.7 }
  variantA: { model: "claude-sonnet-5", temperature: 0.3 }
defaultRule:
  variation: control
targeting:
  - name: internal-staff
    query: tenant in ["acme", "globex"]
    variation: variantA
  - name: gradual-rollout
    percentage:                  # gff 的 map 形式
      control: 70
      variantA: 30
contextFields: [tenant, user_id, model_tier, region]   # golab 扩展
```

**迁移方向**：gff 配置可**单向导入** golab（golab 是其字段超集）；golab 配置**不能**被 gff 消费（存在私有扩展字段）。§4.2 的表述已按此收窄。

### 7.2 定向与约束

约束操作符对标 Unleash 全集，并补齐 AI 场景所需的数值与集合运算：

| 类别 | 操作符 |
|---|---|
| 字符串 | `eq` `neq` `in` `not_in` `contains` `starts_with` `ends_with` `regex` |
| 数值 | `gt` `gte` `lt` `lte` `between` |
| 语义化版本 | `semver_eq` `semver_gt` `semver_lt` |
| 时间 | `date_after` `date_before` |
| 集合 | `has_any` `has_all` `is_subset` |
| AI 专用 | `model_matches` `token_budget_under` `capability_has` |

### 7.3 实验定义

```yaml
key: prompt-v2-fidelity
flag: checkout-model-router          # 绑定的 flag
hypothesis: "v2 prompt 在保持延迟的前提下提升答案忠实度"
primaryMetric: answer_fidelity        # 主指标
secondaryMetrics: [user_thumbs_up_rate]
guardrailMetrics: [p95_latency, token_cost_per_request, error_rate]
allocation:                           # 流量分配
  control: 50
  variantA: 50
sampleSize:
  min: 5000                           # 最小样本量
  maxDays: 14                         # 最长运行时间
statistics:
  method: bayesian                    # frequentist | bayesian | sequential
  alpha: 0.05
  power: 0.8
```

护栏指标的语义：任一护栏指标劣化超过阈值即触发实验告警或自动停止。

### 7.4 AI 资源绑定

flag 的变体不存内容本身，而是**引用 gonacos AI registry 中的资源版本**：

```yaml
aiBinding:
  promptRef:  { id: "prompt-rewrite", label: "canary-v2" }   # → gonacos AI registry
  modelRef:   { provider: "anthropic", model: "claude-sonnet-5" }
  skillRefs:  [ "skill-json-extract@v3" ]
  mcpRefs:    [ "mcp-search@v1.2" ]
  params:
    temperature: 0.3
    maxTokens: 2048
```

`label` 使用 gonacos 的 `BindPromptLabel` 机制 —— 灰度分组与资源版本通过 label 解耦，回滚只需切换 label。

## 8. 评估引擎

### 8.1 评估上下文

```go
type Context struct {
    Key        string            // 分桶主键（必填，通常是 user_id / session_id）
    Tenant     string            // 租户
    ModelTier  string            // 模型档位
    Region     string
    Attributes map[string]any    // 自定义属性
    AI         *AIContext        // AI 专用上下文
}
```

上下文字段分两级：**内置字段**（key / tenant / region）与**工作空间自定义字段**（通过控制台注册，带类型校验）。

### 8.2 分桶算法

**三种实现的实测对照**：

| 来源 | 算法 | 关键细节 |
|---|---|---|
| gff | **fnv32a + mod-N（变模）**：`Hash(flagName + bucketingKey) % maxPercentage`，模数为 `Σpercentage × 1000` | **不是一致性哈希**；**无 hash 版本配置项**；变体桶序为**「变体名逆字母序」**（源码注释自述为 legacy 兼容 HACK），与声明顺序无关 |
| Unleash | MurmurHash3，key 为 **`groupId:id`**（groupId 在前），结果 `(hash % normalizer) + 1`，即 `1..normalizer` | **双 seed**：strategy seed=0、variant seed=86028157。注意 `normalizer` **不是固定 100** —— strategy 分桶在调用点硬编码 100，**variant 分桶用的是全部变体权重和**（可达 1000），实现时勿混用 |
| GrowthBook | fnv32a **双重散列 + 固定模 10000**：`fnv32a(fnv32a(seed+value)) % 10000 / 10000` | v1 为单次散列 + 模 1000，**有并行实验偏差**；v2 修复 |

**golab 的选择：固定模 10000（GrowthBook v2 语义）**

不采用 gff 的变模设计，因为它有一个实质缺陷：

```text
模数 = Σpercentage × 1000   →  修改分配比例会改变模数
                            →  落在旧区间外的用户全部被重排
```

这正是 sticky bucketing 要解决的问题。而单纯加缓存无法修复：已缓存用户拿旧变体、未缓存用户按新模数重算，**两拨人不一致会直接制造 SRM**。

因此：

- golab 内部统一走**固定模 10000**，改比例不影响已有用户的落桶。
- **gff 兼容作为一次性迁移映射**：导入 gff 配置时按其原算法计算一次并固化结果。不做运行时双算法共存 —— 两者散列次数与模数均不同，无法同时复用。
- 采纳 Unleash 的**双 seed 设计**（策略分桶与变体分桶解耦）。

```text
策略命中：hash(groupId, contextKey, seed=0)         <= rollout × 10000
变体分配：hash(groupId, contextKey, seed=86028157)  → 按固定区间表定位变体
```

**粘性（sticky bucketing）语义**（对标 GrowthBook —— **gff 无此能力**）：

| 机制 | 说明 |
|---|---|
| 主 / 次属性 | 主 hash 属性为空时回退到 fallback attribute（如匿名 cookieId） |
| `bucketVersion` | 强制重新分桶的版本号 |
| `minBucketVersion` | sticky 版本低于此值的用户被**排除出实验**（用于清理受污染用户） |
| 求值顺序 | 命中 sticky 值则**跳过** filters / namespace / 条件判断与哈希计算 |

**粘性解析顺序**（对齐 Unleash）：

1. `default` → 依次取 `userId` → `sessionId`
2. 显式 `userId` / `sessionId` → 字段缺失则判定 false
3. 两者都无 → 返回随机数，**粘性不保证**（须在 SDK 文档中明确警示）

**`groupId` 语义**：默认等于 flag key；跨 flag 复用同一 groupId 可关联灰度；**修改 groupId 等于重新洗牌**（可作为重置手段）。**说明**：在固定模方案下，百分比下调后再调回，用户集合天然可完全恢复。

**sticky bucketing**：同一次实验内的分桶结果按 `experimentKey + contextKey` 缓存，避免用户在多次请求间漂移。缓存落 Redis，TTL 与实验周期对齐。

### 8.3 规则匹配顺序

gff 的 `resolution_reason.go` 实际枚举为：`TARGETING_MATCH` / `TARGETING_MATCH_SPLIT` / `SPLIT` / `DISABLED` / `DEFAULT` / `STATIC` / `UNKNOWN` / `ERROR` / `OFFLINE`。golab 在其基础上扩展（**扩展值 gff 原生 SDK 不识别**）：

```text
1. flag 未启用        → 默认变体，reason = DISABLED          [gff 原生]
2. kill-switch 触发   → 默认变体，reason = KILL_SWITCH       [golab 扩展]
3. 定向规则命中        → 命中变体，reason = TARGETING_MATCH   [gff 原生]
4. 渐进发布时间窗外    → 默认变体，reason = OUT_OF_WINDOW     [golab 扩展]
5. 分桶决定变体        → 分桶变体，reason = SPLIT             [gff 原生]
6. 兜底               → 默认变体，reason = DEFAULT           [gff 原生]
```

**注意**：第 2、4 条为 golab 扩展值。若需与 gff 原生 SDK 互通评估结果，须做降级映射（如 `KILL_SWITCH` → `DISABLED`）。

每一步都产出 `resolution_detail`（gff 的 `resolution_detail.go`），用于排查"为什么这个用户拿到这个变体"。

### 8.4 评估入口

```go
// github.com/thomaspoignant/go-feature-flag/modules/core/evaluation
result, err := evaluation.Evaluate[model.JSONType](
    f, flagKey, evalCtx, flagCtx, "json", defaultValue)
// result 类型为 model.VariationResult[T]
```

golab 在此之上封装业务语义：评估结果中的 AI 资源引用会被解析为可执行配置（prompt 内容、模型参数、skill 列表）。

## 9. AI 灰度能力（差异化核心）

### 9.1 灰度对象

| 对象 | 变体维度 | 回滚粒度 |
|---|---|---|
| Prompt | 版本 / label | 切 label |
| 模型 | provider + model + 参数 | 切 modelRef |
| Skill | 版本 / scope | 切 skillRefs |
| AgentSpec | 版本树 | 切版本 |
| MCP Server | 版本 | 切 mcpRefs |
| Pipeline | 版本 | 切版本 |

### 9.2 分层灰度（解决组合爆炸）

prompt × model × params 的组合数随维度指数增长，全组合实验不可行。golab 采用**分层灰度**：

```text
Layer 1 (粗): 模型选择 flag      → 决定用哪个模型
Layer 2 (中): prompt 版本 flag   → 决定用哪个 prompt
Layer 3 (细): 参数微调 flag      → 决定 temperature 等
```

- 每层是独立的 flag，独立评估，逐层解析得到最终配置。
- 定位问题时按层归因：延迟劣化通常来自模型层，质量劣化通常来自 prompt 层。
- **分层流量隔离**：不同层可并行实验，通过互斥流量切分避免相互干扰 —— 复用 GrowthBook 的 Namespace（`[id, start, end]`）与 Filters（seed + ranges + hashVersion）语义（见 6.5）。

**两点必须澄清**：

1. **流量切分（互斥）解决的是干扰，不产生正交性**。把模型层 × prompt 层当作正交会**忽略交互效应** —— 换了模型后 prompt 的相对优劣可能改变，边际结论会出错。要得到真正的正交结论需按**因子设计**安排实验。
2. 这里的真正增量**不是"分层"本身**（GrowthBook 的 Namespace / Filters 正是为重叠、分层实验设计的），而是**配置的组合继承与逐层解析** —— flag 变体引用 AI 资源版本、多层叠加解析出最终配置。那是两家扁平 flag 表达不了的。

### 9.3 指标驱动的自动推进与回滚

gff 的渐进发布是**时间驱动**的（按日期推进百分比）。golab 增加**指标驱动**闭环：

```text
推进条件（全部满足才放量）:
  - 主指标劣化不超过阈值
  - 所有护栏指标健康（延迟/成本/错误率）
  - 样本量达到当前阶段要求

回滚条件（任一触发即回滚）:
  - 护栏指标越界
  - 主指标显著劣化
  - 错误率突增
```

自动推进的每一步都写入变更审计（复用 gonacos 的 `AuditLogger`），支持人工一键回滚到任意历史版本（`Config.HistoryList` + `PreviousHistory`）。

**注意**：`bundle.AuditLogger` 虽为导出字段，但 `server.New` 已在装配时设置了 gonacos 自己的 logger —— golab 直接赋值会**替换**它并使 gonacos 的审计事件丢失，与 `SetPushFunc` 属同类问题（见 16.1）。需要时应**包装**（持有原值并转发）而非替换。

### 9.4 定向规则与 gonacos 灰度的职责分工

**实测确认的边界**：gonacos 的 `GrayRule` 当前实现只解析 `betaIps` 字段做 IP 精确匹配：

```go
// gonacos pkg/config/service.go
func buildBetaRule(betaIPs string) string {
    return `{"type":"beta","betaIps":"` + strings.TrimSpace(betaIPs) + `"}`
}
```

即它表达的是 Nacos 原生的「按 IP 灰度」，**无法承载 `tenant in [...]` 这类通用定向条件**。因此两层职责必须分清：

| 层 | 承载者 | 典型场景 |
|---|---|---|
| 底座级 IP 灰度 | gonacos `GrayRule` | 内部测试、按机器灰度、压测流量隔离 |
| 业务级定向规则 | golab flag 定义内的 `targeting`（见 7.1） | 按用户 / 租户 / 模型 / 预算等任意维度 |

**业务级规则由 golab 评估引擎求值**，不走 `GrayRule` —— 规则语义集中在一处，避免两套求值逻辑并存。

AI 场景的定向条件示例：

```yaml
targeting:
  - name: premium-tenant-gradual
    query: 'tenant in ["acme","globex"] and ai.modelTier eq "premium"'
    percentage: { control: 70, variantA: 30 }   # gff 的 map 形式，见 7.1
```

**说明**：`GrayRule` 是开放 JSON，而 gonacos 只读取 `betaIps`（未知字段被忽略），因此技术上可在同一 JSON 中附加 golab 自有规则以复用其存储与优先级机制。但一期**不采用**该路径 —— 依赖未文档化的"未知字段被忽略"行为过于脆弱。

### 9.5 外部信号驱动的自动降级

参考 Unleash 的 Signals → Actions 机制（signal endpoint + filter 匹配 + action 执行），golab 将其扩展到 AI 场景 —— 这是「AI 应用灰度」相对传统 flag 平台最有价值的运维能力：

| 信号源 | 触发条件 | 自动动作 |
|---|---|---|
| 成本监控 | 单租户 token 成本超阈值 | 切换到轻量模型变体 |
| 供应商健康 | 上游 API 错误率突增 | 切到备用供应商 |
| 配额告警 | 配额剩余低于阈值 | 降级为缓存优先策略 |
| 质量异常 | judge 评分分布突变 | 回滚 prompt 版本 |

```text
外部系统 → POST /api/v1/signals/{name}（token 鉴权 + 速率限制）
            ↓ filter 匹配（复用 constraint 语义）
            ↓ action 执行（切换变体 / 关闭 flag / 回滚版本）
            ↓ 记入变更审计
```

**设计要点**：filter 复用 flag 的 constraint 语义，避免引入第二套匹配语言；action 执行以 service account 身份进行，权限与人工操作一致；每次触发都写入审计日志，保证自动变更可追溯。

## 10. 指标与统计引擎

### 10.1 指标体系

**七种指标类型**（对标 GrowthBook，用 Go 实现）：

| 类型 | 语义 | AI 场景典型用法 |
|---|---|---|
| proportion | 命中事件的单元占比 | 采纳率、点赞率 |
| mean | 单元级聚合值的平均 | 单请求平均成本 |
| ratio | 自定义分母（分子分母可来自不同数据表） | 每千 token 成本 |
| quantile | 分位点比较 | P95 延迟、TTFT P99 |
| retention | 相对首次曝光的留存 | 二次会话留存 |
| dailyParticipation | 活跃天数占比 | 日活使用强度 |
| funnel | 多步顺序完成率（**所有步骤共用同一分母**，避免 post-treatment bias） | 会话→检索→生成→采纳 |

**AI 专属指标族**：

| 类别 | 指标 | 建议类型 | 方向 |
|---|---|---|---|
| 质量 | 忠实度 faithfulness | mean（judge 评分） | 越大越好 |
| 质量 | 相关性 relevance | mean（judge 评分） | 越大越好 |
| 质量 | 幻觉率 | proportion | 越小越好 |
| 质量 | 用户采纳率 | proportion | 越大越好 |
| 成本 | 单请求 token 成本 | mean | 越小越好 |
| 成本 | 缓存命中率 | proportion | 越大越好 |
| 性能 | TTFT（首 token 延迟） | quantile（unit） | 越小越好 |
| 性能 | 端到端延迟 | quantile（unit） | 越小越好 |
| 性能 | 错误率 | proportion | 越小越好 |

每个指标声明：类型、方向、是否护栏、最小样本量、转换窗口。

### 10.2 聚合数据模型

统计引擎只需要三个聚合量，即可支持任意维度重聚合与 CUPED：

```text
sum                 Σ 用户级指标值
sum_squares         Σ 指标值²
sum_cross_products  Σ (主指标值 × 分母值)   [ratio 指标专用]
```

查询返回字段：

| 字段 | 含义 |
|---|---|
| `variation` / `dimension` | 分组维度（无维度分析时 dimension 为 `All`） |
| `users` | 计入该指标分母的单元数 |
| `statistic_type` | `mean` / `ratio` —— 决定方差公式 |
| `main_sum` / `main_sum_squares` | 主指标的聚合量 |
| `denominator_sum` / `denominator_sum_squares` | 分母指标的聚合量 |
| `main_denominator_sum_product` | 协方差项 |

**设计要点**：聚合在 `variation × dimension` 粒度完成，**不存储用户级明细** —— 既满足统计需要，又天然规避 PII 存储。

### 10.3 统计引擎

**双引擎**（组织级 / 项目级切换，默认 Bayesian）：

| 引擎 | 效应估计 | 结论表述 |
|---|---|---|
| Bayesian | 后验分布。先验默认无信息；可开 Proper Prior（默认 N(0, 0.3²)，作用在 lift 尺度，样本量增大后影响衰减） | Chance to Win = 1 − Φ_posterior(0)；CTW > 95% 判胜、< 5% 判负 |
| Frequentist | two-sample t-test（Welch–Satterthwaite 自由度） | p 值 + 95% 置信区间 |

**效应与方差**：

```text
绝对效应  Δ_a = μ_T − μ_C          σ²_Δa = σ²_C/n_C + σ²_T/n_T
相对效应  Δ_r = (μ_T − μ_C)/μ_C    方差用 delta method（因它是比值）
ratio 指标方差需包含 M 与 D 的协方差项
```

**三种差值展示**：Relative（默认）/ Absolute / Scaled Impact（按流量占比折算为全量日效应）。

**基线可选任意变体**，不限定 control。

### 10.4 方差缩减：CUPED 与分层

**CUPED（回归调整）**：

```text
Ŷ_adjusted = Ȳ − θ·X̄        θ = Cov(Y,X) / Var(X)
X = 该指标在实验前窗口的值（lookback 默认 14 天）
```

协变量只用**指标自身的历史值**，不引入其他指标 —— 保持分析管线模块化、可并行。行业参考：Netflix 报告部分关键指标方差降低约 40%。

**Post-stratification（分层）** 三重收益：层内 lift 加权估计总体、层内分流不均时重加权校正、层内分别跑 CUPED。

**AI 场景适用性**：CUPED 对**成本、延迟**类指标收益显著（历史值强相关）；对质量类指标（judge 评分）收益有限。**不适用于** quantile 与 funnel 指标。

### 10.5 序贯检验

固定样本量的问题是无法"边看边停"。序贯检验用**置信序列**替代置信区间：

```text
CI = μ̂ ± σ̂√N · √[ 2(Nρ²+1)/(N²ρ²) · log(√(Nρ²+1)/α) ]
ρ  = √[ (−2log α + log(−2log α + 1)) / N* ]
N  = 两变体样本量之和
N* = tuning parameter（默认 5000，语义为"倾向做决策时的观测数"）
```

**口径提醒**：`N` 与 `N*` 均为**两臂合计**，不是每臂样本量 —— 三变体、希望每臂 3000 时决策，应设 `N* = 6000`。Go 实现若按每臂取值会差一倍。

要点：**不改变点估计，只膨胀标准误**（CI 恒宽于固定样本）；tuning parameter 须在同一实验内保持固定。仅 Frequentist 引擎提供。

### 10.6 多重比较校正

| 方法 | 控制目标 | 适用 |
|---|---|---|
| Holm-Bonferroni | FWER（至少一个假阳性） | 需要可靠性保证 |
| Benjamini-Hochberg | FDR（假阳性占比） | 探索性分析，功效更高 |

**family 定义**：整体结果页 = 所有 goal metric × 所有 variation 构成一个 family；**secondary 与 guardrail 不参与校正**。维度切片独立校正。仅 Frequentist 引擎提供。

### 10.7 健康检查

| 检查 | 算法 / 阈值 | AI 场景补充 |
|---|---|---|
| SRM | 卡方检验，p < 0.001 | 检测分桶或埋点故障 |
| Multiple Exposures | 默认 1% 用户被曝光到多变体 | — |
| Pre-Exposure Bias | 对绝对均值差做 t 检验 + Bonferroni，阈值 0.001 | 验证分桶随机性 |
| Suspicious Uplift | 单指标变化 > 50%（Twyman's Law） | 防埋点 bug |
| Minimum Data Threshold | 每变体最小转化数（默认 150） | 低于阈值不出结论 |
| Variation Id Mismatch | 检测数仓中缺失或错标的行 | — |
| In-Progress Conversions | 识别转换窗口未满的用户 | 避免低估效应 |
| **成本异常** | 单请求成本突变检测 | golab 新增 |
| **质量异常** | judge 评分分布突变检测 | golab 新增 |

### 10.8 样本量与功效

```text
Power(双尾) = 1 − Φ(Z_{1−α/2} − Δ/σ_Δ) + Φ(Z_{α/2} − Δ/σ_Δ)
MDE = 使 power 达到 80% 的最小 Δ（无闭式解，数值求解）
```

**Target MDE 的关键语义**：是否达到目标**只看 CI 宽度，与实测 lift 大小无关** —— CI 落在 0–20% 即已达 10% target MDE，即便实测 lift 为 5%。

实验决策状态机：

| 状态 | 触发 |
|---|---|
| `Unhealthy` | SRM / 多重曝光 / 功效不足 |
| `No data` | 已刷新但无用户 |
| `~X days left` | 未达目标功效，估算剩余时间 |
| `Ship now` | 满足 ship 标准 + 达到 target MDE（或在严格阈值下显著） |
| `Roll back now` | 所有测试变体满足回滚标准 |
| `Ready for review` | 满足评审标准 |

只有 `Unhealthy` 与 `No data` 会在最小运行时长（默认 3 天）之前出现。

### 10.9 Bandits

| 项 | 规则 |
|---|---|
| 算法 | Thompson sampling（按"成为最优的概率"分配流量） |
| 引擎 | 仅 Bayesian |
| 保底 | 每变体至少 1% 流量（防用户行为漂移） |
| 探索窗 | 硬性要求每变体 ≥ 100 用户；建议每变体 ≥ 40 转化 |
| 更新频率 | 最小 15 分钟，建议 daily 或更长 |
| Winner 判定 | 某变体达到 95% 最优概率 |
| SDK 缓存 | 建议至少比更新频率快 5 倍，否则权重陈旧会触发 SRM |

**AI 场景价值**：多 prompt 变体、多模型候选的**自动择优** —— 比固定比例的 A/B 更快收敛到优者，尤其适合 ≥5 个候选的场景；传统实验更适合 2–4 个变体。

**限制**：quantile 指标不可作决策指标；funnel 指标不可用于 bandit 任何位置。

### 10.10 指标采集

```text
SDK → POST /collect（批量事件）
      ↓ 缓冲（内存 + Redis）
      批写入指标存储（PostgreSQL / ClickHouse）
      ↓
      统计引擎按实验分组聚合
```

事件分两类（复用 gff 的事件格式，天然对齐 OpenFeature 规范）：

- **FeatureEvent**（曝光）：携带 `contextKind` / `userKey` / `creationDate` / `key` / `variation` / `value` / `default` / `version` / `source`
- **TrackingEvent**（自定义指标）：携带 `key` / `evaluationContext` / `trackingEventDetails`（另有 `kind` / `contextKind` / `userKey` / `creationDate`）

**归因原则**：变体归因由**服务端分桶结果**决定，不接受客户端上报 —— 避免客户端漂移导致归因错误。

**SDK 侧指标 API**（参考 Unleash impact metrics 的设计，让应用代码能直接声明自定义指标）：

```go
// 应用注册指标，SDK 按周期批量上报
tokens := golab.DefineCounter("golab.tokens.consumed")
tokens.Increment(ctx, float64(usage.TotalTokens))

latency := golab.DefineHistogram("golab.latency.ttft_ms")
latency.Observe(ctx, ttftMs)

budget := golab.DefineGauge("golab.budget.remaining")
budget.Update(ctx, remaining)
```

三类指标：**counter / gauge / histogram**（分位数由服务端从直方图计算）。SDK 自动附加 `appName` / `environment` / `origin` 标签，无需应用手工传。

### 10.11 LLM-as-judge

质量类指标无法用规则计算，通过 judge 管线产出：

```text
采样线上真实请求 → judge prompt → 评分（单点评分 / 成对比较） → 写入 TrackingEvent
```

| 环节 | 工程约束 |
|---|---|
| 采样率 | judge 调用本身消耗 token，按实验阶段动态调整（早期高采样、放量后降低） |
| 位置偏差 | 成对比较时随机交换 A/B 顺序 |
| 长度偏差 | 评分前做长度归一化 |
| 自我偏好 | 避免用被评测的同一模型充当 judge |
| 分数聚集 | 用成对比较替代 1–5 单点评分（判别力更强） |
| 校准 | 定期用人工标注集校准 judge 与人类一致性（Cohen's kappa），低于阈值告警 |
| 执行 | 离线异步管线，不阻塞线上请求 |

## 11. 集成与接口设计

### 11.1 存储映射

| golab 概念 | gonacos 载体 | 接口 |
|---|---|---|
| flag 定义 | config（dataId=`golab.flag.*`） | `Config.Publish/Get/List` |
| flag 历史 | config history | `Config.HistoryList/PreviousHistory` |
| 底座级 IP 灰度 | gray config | `Config.PublishGray/GetGray`（仅 `betaIps` 字段） |
| 工作空间 | namespace | `Namespace.*` |
| 用户与权限 | auth | `Auth.*` |
| AI 资源 | AI registry | `AI.GetPrompt/GetSkill/...` |
| 资源分组 | prompt label | `AI.BindPromptLabel` |

### 11.2 推送链路

**关键限制（实测）**：gonacos 的推送是 **gRPC-only** —— `PushService` 只向已登记的 gRPC `BiRequestStream` 连接写 `ConfigChangeNotifyRequest`，`TrackConfigSubscription` 的唯一调用点在 gRPC 适配层，**HTTP 侧无等价订阅端点**，浏览器无法直接消费。

因此 golab 采用**两段式链路**，SSE 段由 golab-proxy 提供，而非 gonacos：

```text
控制台改 flag
   ↓ Admin API → golab 校验 → gonacos Config.Publish
gonacos PushService（变更产生）
   ↓ gRPC BiRequestStream（Nacos 协议）
golab-proxy —— 注册为 Nacos 协议客户端，接收变更
   ↓ SSE /api/v1/sdk/stream
浏览器 / 边缘 SDK
```

**两条硬约束**：

1. golab **不能**通过 `SetPushFunc` 挂接变更 —— 该方法是**直接赋值**且已被 `server.New` 无条件占用，调用会**静默覆盖** gonacos 自身的推送（见 16.1）。旁路通知须由 golab-proxy 作为 Nacos 协议客户端订阅实现。
2. 浏览器 / 前端 SDK **不能**直连 gonacos 的 gRPC 通道，必须经 golab-proxy 转换为 SSE —— 这与 §11.5 定义的 `/api/v1/sdk/stream` 端点一致。

### 11.3 鉴权与多租户

**重要限制（实测）**：gonacos 的 `Auth.Authorize`（唯一的细粒度鉴权入口）**在全仓库无任何非测试调用点**。实际生效的只有 `pkg/app/auth_middleware.go` 的二值门禁，其文件头自述设计为「permissive for SDK compatibility」：

| 路径 | 要求 |
|---|---|
| `/v3/admin/**`、`/v3/auth/{user,role,permission}*` | 有效 globalAdmin token |
| **其余全部路径** | **无 token 也放行（匿名）** |

且其资源匹配是**精确字符串比较**（无通配、无前缀）。由此产生两条硬约束：

- golab **不能依赖底座做细粒度授权** —— 实验管理员 / 只读 / 发布者等角色必须在 golab 层实现。
- 若把 flag 存在 gonacos config 并**直接暴露其读端点**，**租户隔离在鉴权意义上不成立**。因此 golab 对外只暴露自己的 API，不直接暴露 gonacos 端点。

**落地方案**：

- 工作空间 = gonacos namespace —— 提供**数据隔离**，但不提供鉴权隔离。
- 复用 gonacos 的用户 / 角色 / 权限**数据模型**，以及 `Auth.Authorize(claims, resource, action)` 的调用形态，但**拦截与执行在 golab 自己的中间件**中完成。
- golab 定义资源命名规范（`flag:<key>`、`experiment:<key>`、`workspace:<id>`）并实现**自己的匹配逻辑**（支持前缀与通配，弥补底座的精确匹配限制）。
- SDK 访问使用独立 client token，与管理 API token 分离。

### 11.4 集群与一致性

- 多节点通过 gonacos **内部** Redis pub/sub 同步（`SyncEvent` 模型）；**golab 不调用 `SetSyncFunc`**（见 16.1）。
- flag 变更最终一致，收敛时间取决于 pub/sub 延迟（通常毫秒级）。
- 指标数据独立存储，不参与 gonacos 集群同步。

### 11.5 API 设计

**三类 API，鉴权与限流策略分离**：

| API | 前缀 | 用途 | 鉴权 |
|---|---|---|---|
| Admin API | `/api/v1/admin/**` | 控制台与 CI 调用：flag CRUD、实验管理、指标、审批 | 管理 token + RBAC |
| SDK API | `/api/v1/sdk/**` | SDK 拉取 flag 配置与增量更新 | client token（只读） |
| Collect API | `/api/v1/collect` | 指标事件上报 | client token |

**Admin API 端点族**：

```text
GET    /api/v1/admin/flags                        列表（分页 / 搜索 / 标签过滤）
POST   /api/v1/admin/flags                        创建
```

## 12. SDK 与 OpenFeature

### 12.1 SDK 层

| SDK | 优先级 | 说明 |
|---|---|---|
| Go | P0 | 服务端主力，与 golab 同源 |
| Node / TypeScript | P0 | Web 前端与 Node 后端 |
| Python | P0 | AI 应用主力语言 |
| Java | P1 | 企业集成 |
| React | P1 | 前端 flag 组件 |

**SDK 必备能力**：

| 能力 | 说明 |
|---|---|
| 本地缓存 | 配置入内存，评估不走网络（热路径微秒级） |
| 离线兜底 | 初始化后断网仍用最后一份配置继续工作，仅不再更新 |
| 增量更新 | ETag + delta 拉取；SSE 实时推送 |
| 评估原因 | 返回命中规则与 reason，便于排查"为什么是这个变体" |
| 指标上报 | 周期批量上报（默认 60s），不阻塞业务请求 |
| Bootstrap | 支持从文件或自定义源冷启动，避免首次拉取失败导致功能异常 |

**请求头约定**（对齐 Unleash 生态，便于迁移）：

```text
golab-connection-id: <每实例唯一>    实例追踪与去重
golab-sdk: <lang>@<semver>           SDK 版本统计（用于识别过期 SDK）
golab-appname: <应用名>               应用识别与流量分析
```

**刷新间隔默认值**：配置 15s（服务端）/ 30s（前端）；指标 60s。均可配置。

一期不求 SDK 数量（Unleash 有 8 个后端 + 9 个前端/移动 SDK，GrowthBook 有 24 个），而是保证 P0 语言的行为质量与契约一致性。

### 12.2 基于 nacos SDK 的接入

**不强制使用 golab SDK** —— 对已有 nacos 生态的团队，传输层可以完全复用 nacos SDK。

**可行性依据**：gonacos 已保证 `nacos-sdk-go` 兼容（其 `test/sdkcompat` 与 `examples/` 实测通过）：

```text
配置侧： PublishConfig · GetConfig · ListenConfig · CancelListenConfig · DeleteConfig
注册侧： RegisterInstance · DeregisterInstance · SelectInstances · Subscribe · Unsubscribe
```

而 golab 的 flag 就是 gonacos 中的一条配置（约定 `dataId = golab.flag.<key>`、`group = GOLAB_FLAGS`），因此 nacos SDK 可直接拉取并订阅变更 —— **`ListenConfig` 可用是其中的关键**。

**必须区分两层**：

```text
┌──────────────────────────────────────────┐
│ 传输层：拉取 flag 定义 + 订阅变更            │ ← nacos SDK（gonacos 兼容）
├──────────────────────────────────────────┤
│ 评估层：分桶 / 定向规则 / 变体选择           │ ← golab 评估引擎
└──────────────────────────────────────────┘
```

nacos SDK 提供的是 flag 的**原始定义**（YAML/JSON 字符串），不是**求值结果**。要得到"该用户用哪个变体"，仍需 golab 的评估逻辑。

**两种组装方式**：

**A. golab SDK 内部建立在 nacos SDK 之上**（对使用者透明）

```go
// golab SDK 内部实现
client.ListenConfig(vo.ConfigParam{
    DataId: "golab.flag.checkout", Group: "GOLAB_FLAGS",
    OnChange: func(ns, grp, did, data string) { /* 刷新本地 flag 缓存 */ },
})
variant := golab.Evaluate("checkout", ctx)   // 评估由 golab 完成
```

**B. 应用自行组装**（已有 nacos 生态，不改传输层）

```go
raw, _  := client.GetConfig(vo.ConfigParam{DataId: "golab.flag.checkout", Group: "GOLAB_FLAGS"})
flag    := golab.Parse(raw)           // golab 解析
variant := golab.Evaluate(flag, ctx)  // golab 求值
```

方式 B 是**低成本上车路径** —— Java 微服务等已有 `nacos-client` 的系统，接入 golab 时传输层无需改动，只需引入评估库或调用 HTTP 评估接口。

**两个限制**：

| 限制 | 说明 | 对策 |
|---|---|---|
| 浏览器不可用 | nacos SDK 走 gRPC，浏览器无法直连 | 前端经 golab-proxy 转 HTTP/SSE（见 11.2） |
| 评估逻辑需按语言实现 | Go 可直接复用 gff 的 `modules/core`；Java / Python 需移植 | 或退化为调用 `/api/v1/sdk/eval` 远程评估 |

**结论**：golab SDK 与「nacos SDK + 评估库」是两条**并行**的接入路径 —— 前者能力完整（含指标上报、评估原因），后者接入成本最低。产品上应同时支持，而非二选一。

### 12.3 OpenFeature 兼容

提供标准 OpenFeature Provider，使既有 OpenFeature 用户可无缝切换到 golab。这是对标 Unleash / GrowthBook 的标配能力，也是生态接入的关键。

**上下文映射**：

| OpenFeature | golab |
|---|---|
| `targetingKey` | `contextKey`（分桶主键，优先级最高） |
| `userId` / `sessionId` / `remoteAddress` / `environment` / `appName` | 同名内置字段 |
| `currentTime` | 内置时间字段（缺省取当前时间） |
| 其余属性 | `attributes`（嵌套数组/对象需扁平化，否则丢弃） |

**类型映射**：Boolean ← 布尔变体；String ← string 类型 payload；Number ← number 类型 payload；Object ← json 类型 payload。缺 payload 或类型不符时返回 default value。

**能力边界**（须在 SDK 文档中明示）：Provider **不暴露指标上报与评估 reason** —— 这是对标 Unleash 官方 Provider 的已知缺口。需要完整能力时必须使用原生 SDK。

### 12.4 SDK 契约测试

用同一套 JSON 用例验证所有语言 SDK 的评估行为一致 —— 避免多语言 SDK 语义漂移。

参考 **Unleash 的 `client-specification`（22 个 spec 用例）**，其覆盖范围值得直接对标：各单体策略、多策略组合、多变体、约束操作符、SemVer 操作符、正则、CIDR、自定义粘性、依赖 flag、UTF-8 flag 名称、Delta API（hydration 与 events 两类）。（分桶无专门用例，隐含在 gradual-rollout 与 flexible-rollout 用例中。）

golab 的契约用例在此基础上增加：**AI 资源绑定解析**与**分层灰度逐层求值**的一致性用例。

**验证途径说明**：契约测试验证的是**行为等价**而非代码复用 —— 这一点在 AGPL 约束下尤为重要（见 6.11）。

## 14. 部署与运维

### 14.1 三种形态

| 形态 | 组件 | 适用 |
|---|---|---|
| 单机 | golab + gonacos 同进程（内嵌 miniredis） | 开发、单机部署 |
| 集群 | golab ×N + gonacos ×N + Redis + PostgreSQL | 生产 |
| 边缘 | golab-proxy ×N + 中心控制面 | 低延迟、全球化 |

### 14.2 可观测性

- Prometheus 指标：评估次数、变体分布、推送延迟、SDK 连接数。
- 评估延迟直方图（P99 目标：本地缓存命中 < 1ms）。
- 推送链路追踪。

### 14.3 备份恢复

复用 gonacos 的 `Server.Snapshot()` / `Restore()` 做全量状态备份，flag 与 AI 资源一并落盘。

### 14.4 资源限额

所有限额均通过配置覆盖，避免硬编码；超限时返回明确错误而非静默失败。

| 资源 | 默认上限 |
|---|---|
| flag 数 / 工作空间 | 5000 |
| 环境数 / 工作空间 | 20 |
| 策略数 / flag / 环境 | 30 |
| 约束数 / 策略 | 30 |
| 约束值 / 约束 | 250 |
| segment 数 / 实例 | 300 |
| segment 引用数 / 策略 | 5 |
| 实验数 / 工作空间 | 500 |
| 指标数 / 工作空间 | 200 |
| 渐进发布步骤数 / flag | 20 |

**设计依据**：限额既保护控制面（配置体积直接影响 SDK payload 大小与评估性能），也保护 SDK（payload 过大将拖慢冷启动与内存占用）。

## 15. 实施阶段

### 15.1 阶段划分

1. **契约与骨架**：定义 flag DSL（gff 兼容子集 + 私有扩展）、项目结构、`evaluation` 内核接入。
2. **存储与推送**：接入 gonacos config，打通 publish → push → SDK 拉取链路。
3. **评估引擎**：上下文、分桶、规则匹配、reason 追踪、SDK 契约测试。
4. **管理 API 与控制台**：flag CRUD、灰度发布、评估调试器。
5. **实验与指标**：事件采集、指标聚合、频率派与贝叶斯检验、SRM 检查。
6. **AI 能力**：prompt/model/skill 绑定、分层灰度、label 回滚。
7. **高级统计**：CUPED、序贯检验、bootstrap 置信区间。
8. **LLM-as-judge**：judge 管线、采样控制、一致性校准。
9. **治理**：审批流、变更请求、**授权执行层自建**（底座无 enforcement，见 11.3）、审计。
10. **规模化**：边缘 proxy、多语言 SDK、OpenFeature provider、性能压测。

### 15.2 验收标准

| 维度 | 标准 | 验证方式 |
|---|---|---|
| 契约一致性 | 所有语言 SDK 对同一套 JSON 用例产出相同评估结果 | `test/contract` 用例集 |
| gff 兼容 | 既有 gff 配置文件可直接迁移且评估结果一致 | 用 gff 的 testdata 做对照 |
| 功能覆盖 | 第 6 章矩阵中标注为已覆盖的能力均有对应用例 | 功能 → 用例映射表 |
| 评估性能 | 本地缓存命中 P99 < 1ms | 基准测试 |
| 推送实时性 | flag 变更到 SDK 生效端到端 < 2s | 集成测试 |
| 集群一致性 | 多节点变更最终一致，收敛 < 5s | 多节点集成测试 |
| 统计正确性 | 输出与参考实现在标准数据集上数值一致 | 数值对照测试 |

**统计正确性验证是重中之重** —— 自研统计引擎的最大风险不是性能，而是**算法错误导致错误结论**（比没有平台更危险）。用 GrowthBook 的 `gbstats`（MIT 许可）在合成数据集上做数值对照，是成本最低的正确性保障手段。

## 16. 风险与权衡

### 16.1 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **gonacos 无 LICENSE 文件** | 仓库确无 LICENSE，但两份 README 均声明「MIT（占位 — 发布前确认）」。golab 若公开发布，须先把这个占位落地为正式 LICENSE | 将 README 的 MIT 声明正式化；若改用 Apache-2.0 须先与 gonacos 维护方确认，不可单方面变更 |
| **底座钩子被占用** | `SetPushFunc` / `SetSyncFunc` 是**直接赋值**（非追加），且已被 `server.New` 无条件占用。golab 一旦调用会**静默覆盖**，导致 gonacos 自身的 SDK 推送与多节点同步停止工作，且不报错 | 不调用这两个钩子；旁路通知须包装而非替换（gonacos 无 getter，需在其装配前注入，或上游增加多播支持） |
| 嵌入耦合 | golab 与 gonacos 版本强绑定，升级需同步 | 全部耦合收敛到 `pkg/gonacos` 单一适配层，以接口隔离 |
| **底座鉴权默认放行** | gonacos 的细粒度鉴权无调用点，非 admin 路径匿名放行。若 golab 直接暴露 gonacos 端点，租户隔离失效 | golab 自建授权执行层；只暴露 golab 自己的 API；不依赖底座做细粒度授权 |
| 契约路径依赖 CWD | 嵌入时未实现的 501 stub 不注册，行为与独立运行不一致 | 启动时显式设置工作目录，或提供 contract root 配置项 |
| **依赖 replace 被忽略** | `modules/core` 的 go.mod 含 `replace github.com/nikunjy/rules => hairyhenderson/rules`，而 **replace 指令在依赖模块中会被 Go 忽略** —— golab 实际解析到上游 `nikunjy/rules` v1.5.0，而非 gff 自测用的 fork | 当前可编译；锁定版本并在 CI 中验证规则引擎行为一致性 |
| 统计引擎自研 | Go 重写 7 种指标 + 5 类检验，工作量大且易出算法错误 | 分阶段交付：先 proportion/mean + 双引擎，再补 quantile/CUPED/序贯；用公开数据集做数值对照验证 |
| LLM-as-judge 可靠性 | judge 与人类一致性不足会导致错误结论 | 强制校准流程 + 一致性阈值告警；质量指标不单独作为 ship 依据 |
| 实验样本不足 | AI 应用流量通常远小于 C 端，达到显著性慢 | 默认启用 CUPED 降方差；优先对成本/延迟等高相关指标做实验；多候选场景用 bandit |

### 16.2 关键权衡

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 与 gonacos 的耦合 | 强复用（同进程嵌入） | 复用最大化、上线最快，推送与集群开箱即用 | 部署依赖 gonacos；须先解决 LICENSE |
| 统计引擎实现 | Go 重写（而非复用 GrowthBook 的 Python `gbstats`） | 同栈、可嵌入、无跨语言调用开销 | 须自行实现并验证算法正确性 |
| flag DSL | 以 gff 字段为**子集**基线 | gff 配置可单向导入；评估内核可直接复用 | golab 配置含私有扩展，**gff 无法消费**（迁移是单向的） |
| 指标存储 | 自有（PostgreSQL / ClickHouse）而非数仓原生 | 不绑定 Snowflake/BigQuery，部署更轻 | 失去数仓原生的复用优势，数据量大时须自行优化 |
| Visual Editor | 第一期不做 | AI 应用的 UI 变更需求低于传统 C 端 | 相对 GrowthBook 少一块能力 |
| 前端 | 独立 React 控制台 | 需要实验看板、评估调试器等富交互，难以复用 gonacos console | 开发成本更高 |

### 16.3 差异化定位小结

| 对比对象 | golab 的位置 |
|---|---|
| 相对 Unleash | 功能对齐，并补上它没有的统计引擎与 AI 资源灰度 |
| 相对 GrowthBook | 功能对齐（**其付费功能全部开源实现**），外加同进程嵌入的轻部署与 AI 灰度 |
| 相对 go-feature-flag | 复用其评估内核，补齐控制面、实验分析、权限体系与 AI 能力 |
| 独有能力 | AI 资源版本灰度、分层灰度、成本/质量指标、指标驱动的自动推进与回滚 |

## 17. 非目标

- 不做通用 APM / 可观测平台，指标仅服务于实验结论。
- 不重新实现注册中心与配置中心，全部复用 gonacos。
- 不实现 Nacos v1/v2 老协议（跟随 gonacos 的协议边界）。
- 不内置 LLM 推理能力，judge 与生成走外部可插拔实现。
- 第一阶段不做移动端 SDK（仅服务端 + Web + Node/Python）。
- 不做 gff / Unleash / GrowthBook 的配置双向同步（仅提供单向导入迁移）。
