# 许可证据与发布门槛（Issue #6）

## 结论与负责人

截至 2026-10-06，gonacos **许可文件和历史覆盖声明已取得**：上游提交 [`5ac0bf0`](https://github.com/godeps/gonacos/commit/5ac0bf0b6806) 增加 Apache-2.0 `LICENSE`、`NOTICE`，并明确项目原创贡献的授权覆盖旧固定提交 `514208bd40a131b5badb830bff2daf704ab97ee9`。GoLab 已固定到含许可证文件的新版本。负责人：[cinience](https://github.com/cinience)（GoLab Issue #6 assignee）。许可证据的机器门槛可以验证；对外发布仍需负责人核对所包含第三方文件的声明和实际分发物，其他安全验收项另行判断。

## 版本与证据

- GoLab 根 `LICENSE`、Python `pyproject.toml`、TypeScript `package.json` / `package-lock.json` 均声明 Apache-2.0；这只适用于 GoLab 自有代码。
- `go.mod` 与 `go.sum` 固定 gonacos 伪版本 `v0.0.0-20261006082753-5ac0bf0b6806`；对应 [上游提交](https://github.com/godeps/gonacos/commit/5ac0bf0b6806)。该树内有 Apache-2.0 `LICENSE`、`NOTICE`，上游中英文 README 都明确覆盖旧固定提交中的项目原创贡献。GoLab 不再依赖旧树的 MIT 占位文字；旧树本身仍无许可证文件，历史适用范围由新提交的权利声明提供。
- [`third_party/licenses.json`](../third_party/licenses.json) 记录 `go list -m all` 的完整选定模块图（含测试/工具依赖）、两个发布命令实际引用的模块、模块替换、TypeScript 锁文件版本和每个运行时许可/NOTICE 文件的 SHA-256。[`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) 是运行时第三方声明。源码以本地模块缓存内选定版本为依据；`go.sum` 提供模块内容完整性证据。许可类型是自动初筛，最终应由发布审核人复核原文。
- TypeScript 锁文件的包是开发工具，不随 Go 二进制发布。Python SDK 无运行时第三方依赖，测试工具 `pytest` 不在发布范围。若将来单独分发 SDK 或附带依赖，需按其实际打包内容再生成对应声明。

## 分发义务与机器门槛

运行时依赖目前初筛为 MIT、BSD-2-Clause、BSD-3-Clause 和 Apache-2.0。源码分发应保留适用许可、版权和 NOTICE；二进制分发应随包交付相应许可文本和署名，并按 Apache-2.0 的 NOTICE / 变更声明要求处理。`make dist` 先运行 `make release-check`，再构建二进制，打包根 LICENSE、README、第三方清单、各模块许可/NOTICE 全文。当前 gate 对 gonacos 固定版本及 LICENSE/NOTICE 哈希进行核验，不读取 README 占位。

CI 的 `License evidence` workflow 在 `go.mod`、`go.sum`、TypeScript 锁文件及清单变化时重新计算并比对版本、运行时范围、许可文件哈希和声明；变更需运行 `python3 scripts/license_audit.py update` 后人工审查 diff。`make license-check` 与 `make release-check` 现在要求被固定的 gonacos 版本具有 Apache-2.0 `LICENSE` 和 `NOTICE`；未来升级仍需审查贡献和第三方文件范围，不得只改固定版本字符串。

本次复验：许可证审计的 4 项测试、`go test ./... -count=1`（真实 PostgreSQL/Redis）、`go vet ./...`、`make release-check`、`make dist` 均通过。生成的本地 `dist/golab` 含两个二进制、GoLab 自身 LICENSE、第三方清单和 gonacos 的 `104-LICENSE`、`104-NOTICE`，两文件 SHA-256 与清单一致。此处是打包验证，尚未对外发布。

## 后续升级或授权范围发生争议时

1. **替换 gonacos**：通过 `internal/configstore` 和 `internal/ai` 适配界面引入有明确授权的配置/AI 底座，迁移不可变 revision、manifest、SSE/轮询收敛、AI prompt 版本与摘要及双节点恢复。工程粗估为数周级改造并需重跑 `test/smoke`、`test/e2e`、`test/cluster`、`test/boot`；实际工作量需原型验证。
2. **隔离或商用授权**：进程隔离不能替代适用的使用、复制或分发许可；若现有 Apache-2.0 声明被权利人否认或特定第三方文件不在该范围内，需要单独厘清并由负责人审查。
3. **停用依赖功能**：若不再包含 gonacos 代码，需证明构建、二进制和部署都不含该模块，并重写相应配置及 AI 功能/测试；单纯关闭运行时开关不足以解决已链接二进制的分发问题。

Issue #6 的最终验收应附上游提交、适用版本与第三方文件范围、更新的清单，以及成功的 `make release-check` / `make dist` 证据；负责人确认实际分发物和声明一致后再关闭 issue。该许可证据验收不代替原生 gRPC 租户鉴权等安全验收。
