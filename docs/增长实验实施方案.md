# 增长实验完整实施方案

> 状态：分阶段实施中，2026-10-13。本文是 [能力规划](增长实验规划.md) 的落地方案；以代码、OpenAPI 和测试判断当前能力，未完成的章节仍是设计目标。

### 当前实施进度

指标目录的版本化存储、管理 API、双人审批、实验引用冻结与报告哈希核验已提交。控制台已接入指标目录和主指标版本选择。主指标与护栏可采用不超过实验分析窗口的不同冻结归因时长；报告从同一原始事件快照逐指标重放，SQLite 重启用例已覆盖短窗口边界与长窗口护栏。显式曝光基础协议已覆盖服务端、Go/Python/TypeScript SDK 与控制台模式选择：远程求值返回短时不透明凭据，本地 Go SDK 的 assignment 由服务端重算校验，同批显式曝光原子入库。采集 API 已返回与输入顺序一致的逐事件状态及固定错误码；Go SDK 据此分别记录成功和被拒曝光，Python/TypeScript SDK 校验结果顺序并分别计数部分成功与拒收。聚合诊断 API 已能分别计算随机分配和实际曝光 SRM、未触达、跨变体与分配不一致；onRender 固定分流报告将这些问题作为自动放量阻断。bandit 的 onRender 报告现在也因触达漏损、跨变体或分配不一致而冻结，保留独立的自适应平衡检查。报告内的 Web 诊断摘要及可分享的独立诊断页已接入；采集拒收及重复原因的持久化计数已接入诊断 API 和 Web，按已知实验当前 epoch 的提交尝试统计，重试会重复计数。有限数据导入仍待实现。PostgreSQL 集成测试在本机因测试容器未就绪而未能验证；JSON、SQLite 和相关 API/Web 契约的定向测试已通过。

## 1. 目标、范围与现状

目标是在 Grayling 已有的 Flag、实验预注册、采集、报告和放量能力上，建立“稳定分配 → 真实曝光 → 可复用指标 → 可解释的数据质量 → 审慎放量”的完整链路。第一条业务链路是新用户引导的首次关键操作完成率，并以 D1 留存作为护栏。业务服务负责身份、页面及业务动作；Grayling 负责实验与发布决策，不承担 CRM、营销自动化、全量用户画像或通用事件仓库。

| 能力 | 现状（代码依据） | 本方案新增 |
| --- | --- | --- |
| 实验契约 | `internal/platform/types.go` 的 `Experiment` 内嵌 `MetricSpec`、`GuardrailSpec`，有 `RegistrationVersion`；`internal/platform/experiments.go` 创建时冻结实验口径 | 可复用、不可变的指标目录；实验引用确定的指标版本及快照 |
| 求值和曝光 | `pkg/sdk/client.go` 求值后自动入队曝光；`internal/api/sdk_handlers.go` 远程求值自动记录曝光 | 实验预注册 `onDecision`/`onRender`；显式曝光与分配诊断分开 |
| 采集 | `POST /api/v1/collect` 接受实验事件，按 `eventId` 去重，单位在服务端 HMAC 化 | 可验证的显式曝光凭据、明确的语义去重、事件名称目录与拒收诊断 |
| 分析 | `internal/experiment/report.go` 区分固定样本、序贯和贝叶斯视图；当前固定分流主分析以随机化曝光集为分母 | 报告固定指标版本，增加分配到触达的漏损与跨变体污染诊断 |
| 存储 | JSON、本地 GORM SQLite、GORM PostgreSQL，以及原生 PostgreSQL 后端并存 | 四种后端都定义一致的控制面状态；正式可重算报告仍须满足原始事件和水位条件 |
| Web | `web/app.js` 包含实验创建、评审、绑定、报告和放量；真实浏览器验收见 [报告](acceptance/web-2026-10-08/report.md) | 任务式实验工作台，见 [Web 重设计方案](Web控制台重设计实施方案.md) |

已有指标类型包括 proportion、mean、ratio、quantile、funnel、retention；bandit 有独立报告语义。新增目录先覆盖现有指标类型，不引入新的统计检验。**固定分流与 bandit 不共用“胜出”文案或判断规则。**

## 2. 不可破坏的产品与统计约束

1. 实验的随机化单元、变体、比例、指标及归因规则在一个 epoch 内不变；口径变更创建新版本和新 epoch。指标目录的“最新版本”绝不在运行中自动替换快照。
2. 分配、实际曝光、转化是三种不同事实。远程求值返回变体不必然意味着用户见到组件；后台任务执行成功后才可认为服务端动作生效。报告保留可观察的分配和曝光差异。
3. SRM 在**随机分配层**与**实际曝光层**分别诊断。曝光层偏斜可能来自差异化触达，不能直接断言分流器错误；任一异常都阻止自动推进，待调查后由有权限的人处理。
4. 数据水位、最小样本、最短运行期、护栏、污染检查、原始事件可重算性是结果判定前置条件。异常时输出 HOLD 或暂停原因，不生成虚假的胜出结论。
5. 固定样本 p 值、序贯结果和贝叶斯后验保持分区展示。现有自动放量决策语义不得被新 UI 偷换为后验“胜率”。
6. Admin RBAC、双人审批、作用域、配额、审计和令牌安全继续由服务端执行。Web 隐藏按钮只是辅助，不是权限边界。

## 3. 核心领域模型

### 3.1 指标目录

新增 `MetricDefinition`，键为 `(workspaceId, key, version)`，只允许创建新版本，不允许原地修改已发布版本。字段：`displayName`、`description`、`owner`、`kind`、`source`、`eventKeys`、`unit`、`aggregation`、`dedupUnit`、`direction`、`attributionWindow`、`timezone`、`valueBounds`、`createdAt`、`createdBy`、`status`。`kind` 对齐现有 `MetricSpec.Type`；类型专属参数沿用现有 ratio、quantile、funnel、retention 定义。`source` 第一版仅为 `collect`；P3 再增加 `import`。`status` 为 draft/published/deprecated；deprecated 只禁止新引用，不影响旧报告。

创建实验时请求提交 `primaryMetricRef: {key, version}` 和每个护栏的 `metricRef`。服务端读取已发布定义，验证环境事件命名、随机化单元和统计参数，生成现有 `MetricSpec`/`GuardrailSpec` 快照写入实验，并保存引用。对外读模型同时返回 `metricRefs` 和快照。`RegistrationVersion` 计算范围加入引用与快照；历史实验无引用时按内嵌定义读取，标记 `legacyInline`，避免将旧实验伪装为目录指标。

指标校验：key 在工作空间内稳定；同一版本的定义规范化后生成 hash；不允许改变已发布版本；归因窗口不得超过实验分析窗口或保留策略能支持的范围；漏斗步骤和留存 cohort/return key 必须存在于目录中的事件名；收入等数值型事件声明单位和上下界；主指标及护栏的分母必须明确为随机化且已触达的实验单元，其他分母只进入探索性分析。跨环境复用目录时，环境只控制事件来源是否可用，不复制指标定义。

### 3.2 曝光模式与决策凭据

新增实验字段 `exposureMode: onDecision | onRender`，创建后在该 epoch 不可修改。默认值保留当前行为 `onDecision`，但新建实验向导必须要求用户确认适用场景。`onDecision` 仅用于“求值决定必然生效”的服务端请求；`onRender` 用于页面/响应可能未真正展示或异步任务可能失败的场景。

新增不可变 `Assignment` 事实：`decisionId`、工作空间/环境、实验/epoch、flag/revision、unitHash、variant、`source`、allocation mode、分配时间、凭据截止时间和凭据版本。随机规则来源才进入随机化诊断；targeting/default 仍单列。`onRender` 求值产生 Assignment，但**不写 exposure**。服务端返回 `decisionId` 和短时、作用域绑定的**不透明随机** `exposureToken`。当前实现采用随机 nonce 的 AES-GCM 加密认证载荷，浏览器无法解码原始 unit 或可关联的 unitHash；服务端保存 Assignment 原始事实，以其中的 decisionId 和作用域核验 token，按固定曝光事件 ID 幂等去重。该实现不额外存储 token 明文或 token 哈希，仍满足过期拒收和安全重试。业务服务确认触达后调用显式曝光接口；浏览器仍走业务后端或受控代理，不持有 collect 凭证。

本地 SDK 无法在离线求值时取得服务端 token：SDK 将分配事实与显式曝光放入同一可靠采集管道，服务端用已发布快照的 flag revision、unit 和分配参数核对，并在同一事务内接受分配再接受曝光。此核对用于发现集成错误，不证明持有 SDK 凭证的客户端真实展示了页面；真实触达仍由可信业务代码负责。过期或无法验证的本地快照不得被归入确认性分析；诊断显示拒收原因。重试沿用稳定 `decisionId` 和 `eventId`，不可每次重试生成新 ID。Go SDK先实现，Python/TypeScript 按同一协议跟进。

服务端应把一次决策的首次有效曝光作为效果分析入口。对同一 `(experimentId, epoch, unitHash)` 的相同变体重复展示保留事件量但只计一个分析单元；不同变体的曝光标记污染，报告 HOLD，不能通过简单丢弃其中一臂掩盖。若业务确需“每会话曝光”，必须在注册时明确新的随机化单元或另建专门指标，不能偷偷改主分析分母。

### 3.3 事件与归因

沿用现有 collect envelope 的 `eventId`、`type`、`experimentId`、`epoch`、`variant`、`unit`、`metricKey`、`clientTime`。新增 `decisionId`、`exposureToken` 或本地 SDK 可验证的 assignment payload，以及 `eventKey`。`metricKey` 是指标定义；`eventKey` 是业务动作名，二者不可混用。服务端将本地采集的原始 `unit` 转为工作空间 HMAC 后再持久化；报告、诊断列表不得返回原始 ID。

转化接收顺序：先检查身份与作用域，再检查实验状态/epoch/变体、事件名和指标版本、72 小时迟到与 5 分钟超前规则、`eventId` 幂等，最后按首次有效曝光和归因窗口纳入分析。迟于曝光但尚未匹配的转化允许暂存为“待归因”还是直接拒收，P1 评审必须选定一个策略；**本方案选直接拒收并返回 `missing_exposure`**，便于发现埋点顺序错误。离线批量上报必须按决策、曝光、转化顺序发送，批内按逻辑顺序处理。

新增 `GET /api/v1/admin/experiments/{id}/diagnostics`，只返回聚合计数：分配、已触达、未触达、转化、重复、各拒收原因、跨变体污染、按 source 分层 SRM、数据水位与最近成功采集时间。禁止通过该接口按用户 ID 枚举。超过基数阈值的诊断只出汇总，避免高基数表和敏感信息泄漏。

## 4. API、SDK 与错误契约

以下是**拟新增或扩展**的接口；路径和字段须在实现同一 PR 中写入 `openapi.yaml`，不能把文档草案当现有能力。

| 接口 | 权限与用途 | 关键请求/响应 |
| --- | --- | --- |
| `GET/POST /api/v1/admin/workspaces/{ws}/metrics` | `report.read` / `experiment.write`；列出或创建指标 draft | `key`、`version`、`kind`、定义 hash、status；列表支持搜索与分页 |
| `GET /api/v1/admin/workspaces/{ws}/metrics/{key}/versions/{version}` | `report.read`；查看不可变定义 | 返回定义、引用实验数与审计信息 |
| `POST /api/v1/admin/workspaces/{ws}/metrics/{key}/versions/{version}/publish` | `experiment.write`，涉及确认性指标时走现有审批政策 | 只改变 draft → published；记录 actor、hash、理由 |
| `POST .../experiments`（扩展） | `experiment.write` | 接收 `metricRefs`、`exposureMode`；返回解析后的快照与校验结果 |
| `POST /api/v1/sdk/eval`（扩展） | SDK 凭证 | `onRender` 响应带 `decisionId`、`exposureToken`、`expiresAt`，不自动曝光 |
| `POST /api/v1/collect`（扩展） | collect 凭证 | 接收显式曝光/分配事实；批次响应除总数外增加逐事件安全错误码，保持 `eventId` 幂等 |
| `GET .../experiments/{id}/diagnostics` | `report.read` | 聚合健康诊断、版本、水位、生成时间 |
| `GET .../experiments/{id}/report`（扩展） | `report.read` | 增加固定的指标引用、曝光模式、诊断摘要和报告版本 |

错误码至少区分 `invalid_exposure_token`、`expired_exposure_token`、`assignment_mismatch`、`metric_version_unavailable`、`missing_exposure`、`cross_variant_exposure`、`stale_epoch` 和 `duplicate_event`。HTTP 400 用于请求格式和不可恢复的语义错误；409 用于 epoch/状态冲突；鉴权仍用 401/403；429 保留配额含义。批量采集的部分成功用 200 与逐事件结果表达，客户端只重试可重试项，不能整批换新 ID 重发。

SDK 新增统一的 `EvaluateWithoutExposure` / `TrackExposure(decision)` 能力；已有 `Evaluate` 在 `onDecision` 实验继续自动曝光，在 `onRender` 实验必须只返回决策并要求显式曝光，防止调用旧方法绕过预注册模式。API 命名在各语言遵循其惯例。决策对象显式携带 `exposureMode`、`decisionId` 和可采集标识。OpenFeature Provider 的 `Track` 仍负责业务转化；显式曝光由 Provider hook 或 Grayling SDK 的独立方法完成，不能把任意业务 Track 事件当作曝光。SDK 需提供队列丢弃计数、flush/close 和被拒事件的可观察性。

## 5. 存储与迁移

控制面新增 `metric_definitions` 和 `experiment_metric_refs`。定义行按工作空间、key、version 唯一，JSON payload 保存规范化定义和 hash；索引支持工作空间、状态、key 的列表查询。实验引用既存独立索引，也固化在 Experiment JSON 快照中，防止读模型与分析口径分离。事件面新增 `assignments` 或等价原始事实账本，唯一键为作用域 + `decisionId`，分析索引为实验、epoch、unitHash、时间；曝光事件仍进入现有 `events`。短期不透明 token 不持久化明文；加密认证载荷以 Assignment 事实核验，过期后拒收。轮换签发策略不影响已记录的曝光事实。

原生 PostgreSQL 的迁移追加版本号，使用事务创建表、唯一约束和索引；按现有分区/保留策略处理新事实。GORM SQLite/PostgreSQL 新增模型并迁移，核对唯一约束和事务语义，不能只依赖 `AutoMigrate` 猜测历史表变化。JSON 后端给出序列化字段、原子保存及重启恢复测试。四后端迁移均遵守“先读旧实验、再写新字段”：旧实验的 `exposureMode` 视为 `onDecision`、指标视为 `legacyInline`；不回填虚构 assignment。旧报告可读，只有新建且启用目录引用的实验使用新判断门。

事件保留期必须覆盖“最长分析窗口 + 最大迟到窗口 + 排障/重算缓冲”。现有默认 30 天若不足，创建实验时阻止确认性报告配置，或要求明确提高保留期。正式上线前在 SQLite 与 PostgreSQL 上验证重算；JSON 后端只提供开发预览，不能被 Web 文案标为正式可重算。

## 6. 报告和自动放量门

先在报告构建前读取实验的冻结快照，校验 hash 与 `RegistrationVersion`。按新原始事实重建随机化分配集、触达集、有效转化集，再运行现有统计方法。主分析分母为预注册随机化单元中**实际曝光的唯一单元**；分配到未触达单元进入诊断。对于曝光模式为 `onDecision` 的旧实验，沿用既有数据语义并明确标记。单元跨变体、分配与曝光标签不一致、原始事实不完整、SRM 或水位不足均使报告不健康。

报告顶部必须给出 `verdict`、是否可自动推进、阻断原因、生成时间、实验/epoch、指标版本和数据水位。详细视图分为：样本与触达、主指标及置信区间、护栏、数据质量、预注册口径、探索性方法。无样本显示 HOLD；最短运行期或留存 cohort 未成熟显示“等待”；未满足可重算条件显示“仅预览”。带有异常的绝对提升值仍可供排障查看，但不得用成功色或“胜出”措辞。

放量引擎在每个 step 读取同一版本的报告和健康门。`report.Healthy=false`、SRM、污染、漏损超阈值、水位未到、样本不足或任何护栏破线时暂停并写审计与可读原因。这里的“漏损超阈值”需要在实验预注册时指定阈值；若未配置，先以异常提示和人工 HOLD 处理，不使用拍脑袋的全局数字。人工接管仍记录操作者、理由、报告版本和风险提示；紧急回滚路径不等待统计结论。

| 6 | 有限数据对接 | 独立导入作业与导出接口 | 源记录可追溯、同一事件幂等、重算一致、跨租户隔离；需求不足可延后，不阻断 1–5 |

每个工作包提交代码、OpenAPI/SDK 文档、迁移说明、关键测试和一条真实业务场景验收记录。前一包门槛通过才进入下一包。P0 中发现的身份/触达口径问题须先修正业务契约，不得靠统计界面掩盖。

P3 导入采用受控批次接口或作业：每行只接收 `{sourceId, eventId, experimentId, epoch, unit, eventKey, value, occurredAt}`，在入口换算工作空间 HMAC 并以 `(workspace, sourceId, eventId)` 幂等；源系统对重放、撤销和修正提交新版本，不能直接覆盖已用于确认性报告的事实。导入报告列出读取行数、接受/拒收、最老/最新时间和源水位，失败批次不得推进分析水位。结果导出使用只读 CSV/JSON，包含工作空间、环境、实验、epoch、指标版本、报告版本、健康状态、生成时间和各变体汇总，不导出单元级明细。

## 8. 测试矩阵与上线门槛

- **领域与存储**：指标版本不可变；引用快照与注册 hash 一致；四后端同一实验数据集生成同一业务结果；并发创建版本、事件重试、进程重启、迁移升级与回退读取。
- **安全**：错误工作空间/环境、伪造/过期凭据、原始 unit 泄漏、浏览器管理凭证暴露、低权限读指标、审批自批、配额耗尽、过大批次。
- **统计**：A/A、正常 A/B、分配 SRM、触达 SRM、跨变体、缺失曝光、迟到事件、窗口边界、D1/D7 未成熟、funnel/ratio/quantile、bandit 冻结、无样本、旧实验。
- **SDK**：Go/Python/TypeScript 本地与远程求值、`onDecision`/`onRender`、重复渲染、关闭前 flush、队列溢出、网络断开重试、OpenFeature Track。
- **发布**：自动推进门、护栏破线、人工接管、紧急回滚、双人审批、审计关联到报告版本；多副本同时采集及 leader 切换。
- **产品**：真实浏览器以管理员、分析员、只读者分别走创建、复核、绑定、运行、报告、放量；390px/768px/1440px 中英文、键盘与屏幕阅读器关键路径；无样本/错误/权限不足/网络中断。

上线采用内部试点 → 单工作空间 → 多工作空间。先只开放目录读写与报告展示，再开放 `onRender` 显式曝光，最后开启自动门；每一阶段都有开关和回退路径。回退为禁止新模式、停止自动推进、保留已有事件与审计，旧 `onDecision` 实验继续可读；不删除已写的历史事实。上线观测至少包括采集接受率、拒收原因分布、SDK 队列丢弃、报告重算耗时、诊断水位和放量暂停原因，维度限于工作空间/环境/实验的受控聚合。

## 9. 实施默认值与变更程序

| 决策点 | 本方案采用的默认值 | 变更条件 |
| --- | --- | --- |
| 远程 `onRender` token | 15 分钟有效；过期须重新求值；随机 nonce 加密载荷与持久化 Assignment 事实关联，固定曝光事件 ID 保证重试幂等 | 异步触达场景实测确需更长时，按场景提高并增加滥用评估 |
| 原始事件保留 | 至少 `analysisWindow + 72 小时迟到 + 7 天排障缓冲`；不足则禁止启用确认性自动推进 | 监管或存储成本有额外要求时用工作空间策略覆盖，不能低于可重算门槛 |
| 曝光漏损 | 不设通用“正常”百分比；缺少预注册阈值时只显示差异和人工 HOLD，不能自动推进 | 试点得到按场景区分的基线后，为新实验预注册阈值 |
| 指标定义发布 | 所有 published 新版本经过现有双人审批；draft 可由 `experiment.write` 创建，只有 published 可作为确认性指标 | 若审批负担证据明确，可按风险级别拆分，但须保留审计与职责分离 |
| P3 导入 | 每小时批次；同一源有单调水位，超时/失败不前移；仅导入实验指标事实 | 真实源系统不支持该节奏时，先按可重算和迟到门槛评估 |

这些默认值进入对应配置和 OpenAPI 文档。若实施中需要改变，应写 ADR，列出选择、数据迁移、统计口径及测试后果；已运行 epoch 的确认性契约不能被配置变更追溯修改。
